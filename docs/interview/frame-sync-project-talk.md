# 帧同步项目面试讲解提纲

## 一句话介绍

我实现了一个双客户端确定性篮球 Demo：服务器只转发输入，客户端以相同定点数逻辑推进；远端输入迟到时通过完整世界快照回滚重演，并把稳定快照复用于赛后精彩回放。

## 1. 确定性状态边界

同步世界只保存会影响未来模拟的状态：球员位置、朝向、状态、持球标记，以及篮球位置、速度、状态和持球者。帧号使用整数，空间量使用 `FixedInt` / `FixedVector3`。Unity Transform、墙钟时间、浮点插值和 GUI 全部留在表现层，避免平台和帧率差异进入逻辑。

## 2. 为什么使用零输入预测

远端输入未到时预测“本帧没有新操作”，实现简单、可解释，而且不会凭空制造投篮或拾取边沿。缺点是远端持续移动会短暂停顿，所以表现层额外缓冲一帧并插值。预测错了不在当前状态上打补丁，而是回到确定快照重新演算。

## 3. 为什么必须是完整快照

只恢复位置会遗漏朝向、FSM、持球标记、篮球速度和持球者，重演后仍可能分叉。`FrameSnapshot` 因此覆盖整个会影响后续结果的世界。回滚时恢复错误帧之前的快照，替换真实输入，再逐帧调用同一个 `FrameSimulationSystem` 重演。

## 4. Canonical Frame 与 WorldHash

网络收发帧和本地逻辑帧可能有偏移。Canonical Frame 把比较、日志和哈希统一到同一帧语义，避免“状态相同但比较错帧”。WorldHash 使用 FNV-1a 64 位对规范帧号和同步字段计算摘要，用于快速发现与证明收敛，而不是代替状态恢复。

## 5. 逻辑与表现分离

逻辑层立即得到确定位置；表现层分别处理本地低延迟、远端固定缓冲、插值和回滚纠正平滑。表现组件只能读逻辑结果，不能写回同步实体。这样视觉层即使换成不同插值策略，也不会改变 WorldHash。

## 6. 稳定帧门竞态修复

精彩回放不能采集仍可能被回滚的预测帧。`StableRemoteFrameGate` 只有在远端真实输入已验证且纠正提交后才推进，`StableFrameCursor` 再按连续顺序消费。关键竞态是“输入已到，但对应回滚尚未完成”；门在纠正提交前不能把该帧标记稳定，否则会永久录入错误快照。

## 7. 历史过期恢复

帧缓冲和高光历史都有容量上限。若稳定游标落后到快照已经淘汰，系统不会伪造片段或无限报错，而是清空不完整片段、将记录器前移到首个仍保留的帧，并记录可诊断原因。恢复后继续采集新的完整片段。

## 8. 共享终局帧修复

仅让双方识别同一个 `F9` 请求仍不够：当请求发生时，两台机器的本地预测头可能不同，直接各自暂停会冻结成两个世界。修复方案是记录器只在所有待收尾片段完成后发布确定的 `PostGameTerminalFrame`。进入回放前，`PostGameTransitionSystem` 强制从预测快照缓冲恢复该帧；缺快照则取消切换，保证“恢复、表现对齐、暂停、换阶段”是全有或全无。

## 9. 取舍与后续

当前服务器不是权威模拟，优先展示纯输入帧同步；固定一帧远端缓冲也没有做动态抖动估计。下一阶段可增加延迟/丢包注入统计、动态缓冲、录像持久化和更完整比赛规则，但应继续遵守同步状态边界并为每个新增状态补齐快照与哈希字段。
