# P1-D 完整世界 Hash 与双端一致性日志设计

## 目标

为 Route C 当前的两名玩家加篮球世界建立可重复、可比较的最终帧 Hash。正常模拟和回滚重演必须对相同帧的相同完整世界产生相同结果，并输出便于双端人工比对的结构化日志。

## 当前问题

现有 `MD5Checker` 实际使用 32 位 XOR，只覆盖两名玩家的 X/Z 位置。XOR 不保留字段顺序，相等字段会抵消；`CheckAndLog` 还把当前检查结果与本机上一次检查结果比较，而不是与另一客户端同帧结果比较。它既不是 MD5，也不能证明完整世界一致。

当前可靠的完整世界描述是 `FrameSnapshot`。它已经覆盖两名玩家的位置、朝向、状态、球权，以及篮球的位置、速度、状态和持有者，并由正常帧和回滚重演共同保存。

## 方案

新增独立静态深模块 `WorldHash`。其公开接口只有：

```csharp
public static ulong Compute(FrameSnapshot snapshot)
```

模块隐藏字段顺序、标量编码、算法常量和 schema 版本。调用方只提交完整快照，不接触字节布局。日志编排留在 `GameController`，因为客户端身份、正常/回滚来源和日志节流属于外层运行时上下文。

旧 `MD5Checker` 保留源码以降低兼容风险，但移除其活动调用点；P1-D 不删除或原地改写旧模块。

## 算法与编码

- 算法：FNV-1a 64-bit。
- schema：`1`，作为第一个 32 位标量参与 Hash。
- 所有整数先按无符号 32 位解释，再按固定小端顺序逐字节混入。
- `FixedInt` 只使用 `_raw`。
- `bool` 固定编码为 32 位整数 `0` 或 `1`。
- 所有乘法在 `unchecked` 语义下自然截断到 64 位。

FNV-1a 用于工程脱同步检测，不用于密码学认证或反作弊。

## Hash 字段与顺序

1. schema version
2. `frameID`
3. 玩家1位置 X/Y/Z
4. 玩家2位置 X/Y/Z
5. 玩家1朝向 X/Y/Z
6. 玩家2朝向 X/Y/Z
7. 玩家1状态、玩家2状态
8. 玩家1球权、玩家2球权
9. 篮球位置 X/Y/Z
10. 篮球速度 X/Y/Z
11. 篮球状态
12. 篮球持有者索引

不包含派生的 `IsValid`、静态 `playerIndex`、Transform、材质、墙钟时间、输入、预测历史、缓冲区内部状态或球场常量。

## 快照接口

`PredictionSystem.TakeWorldSnapshot` 改为返回刚写入缓冲区的 `FrameSnapshot`。原调用者允许忽略返回值，因此现有调用保持兼容。

新增：

```csharp
public bool TryGetWorldSnapshot(int frameID, out FrameSnapshot snapshot)
```

它只读取缓冲区，缺失时返回 `false` 和默认快照，不改变世界。该接口让回滚完成后的调用方读取已重建的最终快照，而不重复捕获或复制字段映射。

## 正常帧时序

1. `FrameSimulationSystem.Step` 完成整帧逻辑。
2. `OnPostFrameUpdate` 保存完整世界快照。
3. 若当前没有待处理回滚，则对该快照计算最终 Hash。
4. 仅在日志间隔命中时输出 `source=normal phase=final`。

若 `_pendingRollback` 为真，正常路径不输出该预测世界的最终 Hash，避免同帧重复和误报。

## 回滚时序

1. `LateUpdate` 调用 `FrameReplaySystem.Replay`。
2. 重演从安全快照或初始世界开始，逐帧调用共享模拟入口并重建快照。
3. 只有 `Replay` 成功返回后，读取 `lastExecutedFrame` 的最终快照。
4. 强制输出一次 `source=rollback phase=final` Hash，不受常规日志间隔限制。
5. 重演失败或最终快照缺失时只输出错误，不输出最终 Hash。

## 日志

正常帧：

```text
[RouteC][WorldHash] schema=1 algo=FNV1A64 localPlayer=0 frame=600 phase=final source=normal hash=0x0123456789ABCDEF
```

回滚完成：

```text
[RouteC][WorldHash] schema=1 algo=FNV1A64 localPlayer=1 frame=604 phase=final source=rollback errorFrame=601 restoredFrame=600 replayed=4 hash=0x0123456789ABCDEF
```

`localPlayer` 只用于标记日志来源，不参与 Hash。常规输出默认每 200 帧一次；人工双端验收可在 Inspector 中把间隔设为 `1`。

## 自动测试

- 固定快照具有锁定的参考 Hash，证明算法和字节序稳定。
- 同一快照重复计算结果一致。
- 25 个世界快照字段分别变化时结果均变化。
- 玩家槽位交换后结果变化，防止无序 XOR 回归。
- `TakeWorldSnapshot` 返回其实际保存的快照。
- `TryGetWorldSnapshot` 对存在和缺失帧分别返回正确结果且不修改世界。
- 权威直接模拟与错误预测后回滚重演，在纠正前 Hash 不同，回滚完成后最终 Hash 相同。
- 现有 EditMode 全量测试继续通过。

## 人工验收

- 两端在静止、移动、持球、投篮、飞行、进球、下落和落地阶段，相同最终帧 Hash 一致。
- 触发预测错误时允许纠正前暂时不一致；回滚完成日志必须追平。
- 回滚只输出一条摘要和一条最终 Hash，不恢复逐帧 FSM 日志。
- 现有篮球行为和操作响应不发生回归，Console 无异常。

## 风险与边界

- 新增同步字段时必须同时扩展快照、Hash 字段和 schema；否则会漏检。
- 64 位 Hash 存在理论碰撞，仅用于诊断。
- 双端必须使用相同玩家槽位顺序和代码版本。
- 本阶段不实现网络传输 Hash、服务器仲裁、自动断线/重连、状态纠正、反作弊、动态玩家数量、比分或计时器。
- 不修改 `E:\帧同步`，不自动 commit、merge 或 push。

## 人工验收修正（2026-08-05）

首次双端人工运行暴露出真实位置漂移。日志证明两端启动时间不同，Player0 与 Player1 各自建立的本地帧偏移并不互为相反数；同时，旧 `ResolveRemote` 会拿“当前帧真值”比较所有历史预测，因而会漏掉 `静止 → 短暂移动 → 静止` 这类已经恢复为当前值的历史输入。漏检后不会触发回滚，位置差会永久保留。

纠正设计如下：

- `PredictionSystem` 对每个可验证的历史预测帧查询该帧自己的远端真值，不再使用当前帧真值近似。
- 同一批到达数据包含多个错误时，只报告最早错误帧并清除其后的预测历史，由一次权威重演修复整个受污染后缀。
- 在旧独立偏移方案中，冷启动阶段首个真实输入基线前的预测不可验证；共同时间线启用后该豁免被取消，因为同号帧真值已经无歧义，帧 0 的错误预测也必须回滚。
- 双端日志采用 Player0 时间线作为统一世界帧：Player0 使用本地帧；Player1 使用 `localFrame - remoteFrameOffset`。日志同时保留 `localFrame` 供诊断。
- `WorldHash` schema 升为 `2`。Hash 中的帧坐标使用统一世界帧，不混入各端不可直接比较的本地帧号。
- 若 Player1 尚未建立远端帧锚点，则暂不输出可比较 Hash，避免制造伪差异。

新增验收重点：短促移动后松键仍必须被发现并回滚；多个历史错误必须一次从最早帧追平；两端同一 `frame` 的最终 Hash 才允许直接比较。

## 共同时间线纠正（2026-08-06）

独立审查证明，只统一日志标签仍不足以统一模拟输入。若两端各自锚定出 `+317/-305`，同一 Player0 世界帧会分别消费 `P1[F-317]` 与 `P1[F-305]`，世界必然无法收敛。

本次追加批准采用共同起跑方案：

- `NetworkServer` 必须先接收两个客户端，之后才向双方发送玩家编号。玩家编号同时作为本局开始信号；任何单独客户端不得提前启动帧引擎。
- 两个客户端收到开始信号后都从逻辑帧 `0` 起跑。网络包中的远端帧号直接对应本地同号帧，运行时远端偏移固定为 `0`，不再根据首包各自估算。
- 正常模拟、历史真值查询、回滚重演、远端输入清理和 WorldHash 日志全部使用同一个共享帧号。
- 若同一 Unity `Update` 在 `LateUpdate` 回滚前发现多个错误，只保留最早错误帧及其精确真值。
- 回滚读取缓冲输入前必须确认输入数组同时覆盖本地与远端玩家槽位；缺失时返回失败结果，不允许抛出越界异常。

明确不做服务器权威状态模拟、动态重连、运行中重新同步、网络 Hash 传输或服务器仲裁。本次协议要求客户端与重新生成的 `NetworkServer.exe` 成套使用。
