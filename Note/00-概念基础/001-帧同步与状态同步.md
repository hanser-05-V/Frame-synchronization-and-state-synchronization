# 001 — 帧同步与状态同步

## 一句话定位

帧同步（Lockstep）和状态同步是实时多人游戏的两种网络模型。**帧同步只传玩家输入**（每帧 4 字节），所有客户端独立运行同一份确定性逻辑；**状态同步由服务器计算游戏状态**，下发结果给客户端展示。街篮2 选择了帧同步，原因是低带宽 + 弱网适应性。

---

## 概念对比

| 维度 | 帧同步（Lockstep） | 状态同步 |
|------|:---:|:---:|
| **传输内容** | 玩家输入（按键/方向） | 游戏状态（位置/速度/动画） |
| **每帧数据量** | 4 字节 × 玩家数 | 200+ 字节 |
| **计算位置** | 各客户端自己算 | 服务器算，客户端只展示 |
| **延迟感受** | 预测掩盖延迟，体验流畅 | 服务器确认后才有反馈 |
| **服务器角色** | 输入中转站 + 校验者 | 游戏世界唯一权威 |
| **断线重连** | 需要追帧（重放所有历史输入） | 直接下发当前状态 |
| **防作弊** | 难（客户端有完整逻辑） | 易（服务器是权威） |
| **确定性要求** | 极高（必须定点数） | 低（服务器说了算） |

---

## 核心要点

### 1. 帧同步 = 传"剧本"不传"画面"

```
帧同步流程：
  客户端A: "帧100，我按了投篮键" ──→ Server ──→ 所有人
  客户端B: 收到 → 自己算 → 球员起跳 → 投篮
  客户端C: 收到 → 自己算 → 球员起跳 → 投篮（结果完全相同！）

状态同步流程：
  客户端A: "我按了投篮键" ──→ Server
  Server: 计算轨迹 → "球员B在(10,5,3)，播动画X，球飞行中"
  ClientB/C: 收到 → 按指令展示（不自己算）
```

### 2. 带宽节省是核心优势

街篮2 每帧每玩家只传 4 字节（一个 `uint`）：

```csharp
// E:\帧同步\Common\Battle\FrameBuffer.cs:38-51
public struct Input
{
    // 32-bit = pos(4) + yaw(8) + btn(7) + flag(5) + emoji(4) + giveup(4)
    public uint _raw;
}
```

一局 3v3（6 个玩家），30FPS，一秒钟网络流量只有 `6 × 30 × 4 = 720 字节/秒`。

### 3. 帧同步的代价：确定性

所有客户端必须运行**完全相同的代码**、用**完全相同的输入**、产出**完全相同的输出**。这就是为什么街篮2 用 `FixedNumber`（定点数）替代 `float`——IEEE 754 浮点数在不同 CPU 上结果可能不同。

### 4. 联网帧同步 = 单机帧同步 + 三个机制

```
单机帧同步                    联网帧同步（加了三个机制）
 输入 → 逻辑 → 渲染            输入 → 服务器转发 → 所有人
                                    │
                                    ├── 预测：不等服务器，本地先跑
                                    ├── 校验：服务器帧到了，对比预测
                                    └── 回滚：不一致 → 退回重算
```

### 5. 为什么街篮2 选帧同步？

- **实时性要求高**：篮球对战需要快速响应，状态同步的服务器确认延迟太大
- **带宽受限**：移动网络下带宽宝贵，帧同步 720 字节/秒 vs 状态同步几 KB/秒
- **录像回放天然支持**：帧同步的输入序列就是录像，不需要额外录制
- **已有确定性框架基础**：定点数学库、ECS 系统、状态机——为帧同步打下了基础
