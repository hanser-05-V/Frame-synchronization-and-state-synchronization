### FixedMath — Q1：`Sqrt` 里 `(long)value._raw * FixedInt.SCALE` 为什么用 `long`？

**帅老大回答：**
转化为 long 避免相乘时精度移除。不用 long 后续计算量变大时会导致丢失精度，当前项目比较简单还没遇到过相关问题。

**评价：** ⚠️ 原因对了，术语混淆，未把前后知识点串联

**❌ 错误点：**
1. **术语：** 不是"精度移除"，是**整数溢出**。`int × int` 结果可能超过 `int.MaxValue`（约 21 亿），高位被截断。这是范围问题，不是精度问题。面试时说错这两个会被认为基础不扎实。
2. **"没遇到过" — 实际上遇到过：** 阶段0 已有一个专门的修复 commit `T_fix_fixedint — FixedInt 溢出修复`，且阶段0考核 Q4 考的就是 `FixedInt 乘法用 long 防溢出`。Sqrt 里用 long 和 FixedInt 乘法里用 long 是**同一原因**。帅老大没把这两个知识点串起来。

**✅ 答对的部分：**
- 核心目的：避免溢出
- 知道 long 是保护措施

**💜 小爱参考回答（面试标准）：**
这是定点数库中一个经典的溢出保护手段。`int × int` 的结果类型仍然是 `int`，如果乘积超过 `int.MaxValue`（约 21 亿），就会发生整数溢出——高位被截断，得到完全错误的结果。比如 `100万的raw × 1000(SCALE) = 10亿`，还在 int 范围内；但如果 raw 本身已经很大（比如表示一个大的坐标值），`raw × SCALE` 就超过了 int 的上限。`(long)value._raw` 把第一个操作数提升为 64 位，整个乘法就在 long 范围内完成，避免了溢出。阶段0 中 FixedInt 的乘除运算符也做了同样的修复（commit: `T_fix_fixedint`）——统一定点数底层的溢出保护策略。面试时可以补充一句：在帧同步里这种保护尤其重要，因为溢出不会抛异常，只会静默产生错误值，导致 MD5 脱同步难以排查。

### FixedMath — Q2：`raw × SCALE` 之后这个 `n` 的含义是什么？为什么不直接用 `value._raw`？

**帅老大回答：**
不清楚。

**评价：** ❌ 未答出，定点数开方数学技巧

**✅ 答案 — 数学推导：**

问题：给 FixedInt `value`（`_raw = 实际值 × SCALE`），求 sqrt，结果也是 FixedInt（`_raw = sqrt(实际值) × SCALE`）。

```
实际值 = value._raw / SCALE
目标结果的 _raw = sqrt(实际值) × SCALE
                = sqrt(value._raw / SCALE) × SCALE
                = sqrt(value._raw / SCALE × SCALE²)
                = sqrt(value._raw × SCALE)
```

所以 `n = value._raw × SCALE`，对 n 做整数 sqrt，结果就是 `sqrt(实际值) × SCALE`。

**为什么不直接用 `value._raw`？例子：**
- `value._raw = 2500`（实际值 2.5）
- 直接用 `_raw`：`sqrt(2500) = 50` → 实际值 = 0.05，但 `sqrt(2.5) ≈ 1.581` ❌
- 用 `_raw × SCALE`：`n = 2500 × 1000 = 2,500,000` → `sqrt(2,500,000) ≈ 1581` → 实际值 = 1.581 ✅

**本质：** 多乘一个 SCALE 是把"开方后要除以 SCALE"的损失提前补偿回来——整数 sqrt 本身不保留小数，通过缩放输入把小数"嵌入"到整数结果里。

**💜 小爱参考回答（面试标准）：**
这是定点数开方的标准技巧。问题的核心矛盾是：我们要求 sqrt 的结果也是 FixedInt（raw = 实际值 × SCALE），但整数开方不会产生小数部分。如果把 `value._raw`（已经是 ×SCALE 的值）直接开方，得到的 raw 偏小了一个 SCALE 因子倍——因为 sqrt(a×SCALE) ≠ sqrt(a)×SCALE。数学上的解法是：`sqrt(a)×SCALE = sqrt(a×SCALE²) = sqrt(a×SCALE × SCALE) = sqrt(raw × SCALE)`。所以先把 raw 乘以 SCALE，再开方，结果天然就是 FixedInt 格式。这是用一次乘法换回完整的 Scale 精度，定点数数学库的经典操作。

### FixedMath — Q3：Newton 迭代收敛条件为什么不是 `next == r` 就够了，还要加 ±1？

**帅老大回答：**
原理是猜-修正-再猜。next 逐渐收敛，当 next==r 就收敛完了，一般 5~8 次就可以。不能去掉 ±1，因为整数除法 / 会有小数，很难 100% 完全相等，在浮动 1 范围内就视为取得平方根，后面多出的小数会舍弃掉。

**评价：** ✅ 核心理解正确，一处术语偏差

**✅ 答对的部分：**
- Newton 法本质：猜 → 修正 → 再猜
- 整数除法 `n/r` 有余数，不容易完全相等，±1 是容差
- 5~8 次基本够，20 次是安全上限
- 不能去掉 ±1

**⚠️ 偏差：**
帅老大说"误差逐渐减半"——但 Newton 法对 sqrt 是**二次收敛**：每次迭代正确位数翻倍（比如第1次 1 位 → 第2次 2 位 → 第3次 4 位），比"减半"快得多。面试用"二次收敛"更精确。

**🦉补充——±1 的根本原因：**
是**整数除法截断效应**，不是泛泛的精度问题。举例：
```
真值 = 1581.3
  r=1581 → next = (1581 + 2500000/1581)/2 = (1581+1581)/2 = 1581 → 停 ✅
  r=1582 → next = (1582 + 2500000/1582)/2 = (1582+1580)/2 = 1581
```
2500000/1582 本来 ≈ 1580.01，整数除法截成 1580 → next=1581。下一轮 r=1581 又算出 next=1581，停止。±1 是**提前退出——知道已进入 1 以内的振荡区间，不必继续**。

**💜 小爱参考回答（面试标准）：**
Newton 法的 ±1 收敛条件是**整数除法截断效应**下的必然设计。理论上 Newton 迭代会越来越接近真值，但整数除法每次都会截断余数，导致在真值附近 ±1 范围内来回振荡而不是精确相等。比如 r=1582 算出 next=1581，下一轮 r=1581 又算出 next=1581——只有把 ±1 都视为收敛，循环才能正常终止。这里的 ±1 不是"精度妥协"，而是适配了整数运算的"最后一次修正"——知道结果已经在整数精度范围内，多迭代也不会更好了。另外 Newton 法对 sqrt 是二次收敛的，每次迭代正确位数翻倍，这就是为什么 5~8 次迭代就够了而不用跑满 20 次。

### FixedMath — Q4：为什么没有 Sin/Cos/Atan2？项目里角度运算怎么处理？

**帅老大回答：**
角度运算是篮球自身行为层面的东西，FixedMath 只完成定点数运算。

**评价：** ⚠️ 方向在但未点出关键设计决策

**✅ 答对：**
- 三角函数不是 FixedMath 的职责

**缺失的关键点：**
**为什么 Demo 不需要三角函数？** 不是"还没加"，是用**向量运算替代了**——项目里已经大量使用了这个技巧：

| 需求 | 不用三角函数的做法 |
|------|-------------------|
| 朝向方向 | FixedVector3 方向向量，不碰角度 |
| 左右判断 | `CrossXZ`（叉乘 y 分量），不碰 Atan2 |
| 距离比较 | `SqrDistance`（平方距离），不碰 Sin/Cos |
| 投射方向 | 向量减法 + normalized，全程无角度 |

**为什么不加三角函数到 FixedMath？**
- Taylor 级数：极慢，每帧调必追帧
- 查表法（LUT）：快但占内存
- **不用三角函数**：最快、最准、100% 确定性

Demo 选了第三种——这是正确的架构决策。

**💜 小爱参考回答（面试标准）：**
FixedMath 没有三角函数不是因为偷懒，而是一个刻意的架构选择。在 3D 空间里，几乎所有"需要角度"的需求都可以用向量运算替代：朝向用方向向量，左右判断用叉积，距离用平方值，投影用点积。这些向量运算只需要加减乘，在定点数下既快又确定。而定点数三角函数要么用 Taylor 级数（极慢，每帧调用必然导致追帧），要么用查表法（精度和内存的权衡）。对于这个 Demo，选"不用三角函数"是正确的设计决策——不是绕过问题，而是用更简单的工具解决了同一个问题。
