### FixedVector3 — Q1：为什么帧同步需要 FixedVector3 而不是直接用 Unity Vector3？

**帅老大回答：**
本质原因是需要确保玩家输入确定。区别于 Unity Vector3，内部使用 FixedInput（应该指 FixedInt）来对三维坐标进行处理，消除 float 在不同设备的影响。

**评价：** ⚠️ 方向正确，有细节错误

**❌ 错误点：**
1. **术语混淆：** 帅老大说成了 "FixedInput"，但 FixedVector3 内部用的是 **FixedInt**。FixedInput 不存在，项目中 `FrameInput` 是按键输入类型，完全不同。面试时说错这个术语会显得对基础类型不熟。
2. **缺了关键的一层：** "消除 float 不同设备的影响" —— 但**为什么** float 在不同设备会有影响？没说清楚。

**✅ 正确的核心原理：**
`float`（IEEE 754）在不同 CPU 架构（x86/x64/ARM）、不同编译器优化等级、不同 .NET JIT 版本（Mono vs IL2CPP）下，同一个浮点运算的**舍入行为**可能产生微小差异。`0.1f + 0.2f` 在 PC 和手机上结果可能差 1 个 ulp（最小精度单位）。帧同步里每帧累积这些差异，几秒后两端状态就完全不同了，MD5 校验就会报脱同步。

而 `FixedInt` 底层是 `int × SCALE`，**整数运算在所有 CPU 上结果完全一致**——`2 + 3` 在 PC 和手机上永远等于 `5`，不存在舍入歧义。

**💜 小爱参考回答（面试标准）：**
FixedVector3 与 Unity Vector3 的根本区别在于**底层数值类型的确定性保证**。Unity Vector3 由 3 个 `float` 组成，float 遵循 IEEE 754 标准，但其运算结果在不同 CPU 架构（x86 vs ARM）、不同编译器（Mono vs IL2CPP）以及不同优化等级下的舍入行为可能不一致，哪怕只差 1 个 ulp，帧同步中每帧累积后两端状态就会完全偏离。FixedVector3 由 3 个 `FixedInt` 组成，FixedInt 底层是 `int × 1000` 的整数，整数运算在**所有平台绝对一致**，没有任何舍入歧义。这就是帧同步选择 FixedVector3 的本质原因：不是"float 不准"，而是"float 跨平台不一致"。帧同步的核心需求是"同一组输入在任何机器上产出完全相同的状态"，FixedInt 保证了这一点。

### FixedVector3 — Q2：为什么 `==` 直接比较 `_raw` 而不是 FixedInt 对象？

**帅老大回答：**
不是很清楚，猜测是没有给 FixedInt 写 `==` 运算符重载方法。

**评价：** ⚠️ 方向偏了

**❌ 错误点：**
- FixedInt 实际上**有** `==` 运算符重载（在 FixedInt.cs 里定义了），所以用 `a.x == b.x` 语法上是可以的。帅老大猜测的原因不成立。

**✅ 正确原因（两个）：**

1. **性能：** `_raw` 是 `int`，int 的 `==` 是 CPU 原生单条指令。`FixedInt == FixedInt` 即使有重载，也要先走运算符方法调用 → 读取 `_raw` → 再比较，多一层间接调用（JIT 可能内联但不保证）。

2. **正确性保证：** FixedInt 是 **单字段 struct**——内部只有 `_raw` 一个字段，没有其他状态、标志位或辅助数据。所以 `_raw` 相等**等价于** FixedInt 相等，不需要绕一圈经过 `==` 重载去确认。直接比 `_raw` 是**绕过封装，直取核心数据**——在你 100% 确定 struct 只有一个字段且语义由它唯一确定时，这是一种确定性优化的常见手法。

**💜 小爱参考回答（面试标准）：**
这行代码看起来绕过了封装，实际上是一个精确的优化决策。核心前提是：FixedInt 是单字段 struct，只有 `_raw`（一个 int），没有其他任何状态。因此 `_raw` 相等就等价于 FixedInt 相等。直接比较 `_raw` 有两个优势：第一，性能——int 的 `==` 是 CPU 原生指令，不需要走 `FixedInt.operator==` 的方法调用（即使 JIT 可能内联，在确定性优先的场景下不应依赖编译器行为）；第二，正确性保证——不需要信任 `==` 重载的实现是否完全正确、是否在未来修改中引入了其他判断逻辑。这是一个"确定性优先于封装性"的经典实践。

### FixedVector3 — Q3：`normalized` 内部执行 `magnitude → Sqrt → 除法`，有什么性能风险？之前碰到过吗？

**帅老大回答：**
不清楚。

**评价：** ❌ 未答出，但项目里已有此问题的优化痕迹

**✅ 答案：**
`magnitude` 的计算链是 `sqrMagnitude → FixedMath.Sqrt()`。FixedMath 的 Sqrt 用 **Newton 迭代法**，需要多轮循环逼近，比加减乘除慢一个数量级。调用 `normalized` 触发一次 Sqrt + 三次除法，帧同步每帧循环中如果多个实体调用，累积开销会导致帧耗时超标。

**你之前碰到过的证据（但没意识到）：**
RESUME 中记载了 `⚡追帧 1 偶发（因 normalized Sqrt 耗时）`——某一帧模拟耗时超过了帧间隔，导致下一帧需要追赶。

**工程规避方式：**

| 方式 | 说明 |
|------|------|
| 用 `sqrMagnitude` 代替 `magnitude` | 比较距离时不求开方，用平方值比较 |
| 避免频繁调用 `normalized` | 方向向量缓存，只在变化时重算 |
| XZ 平面计算用 `sqrMagnitudeXZ` | 省掉 y 分量乘法 |

项目中已做的优化：`SqrDistance()` 和 `SqrDistanceXZ()` 就是绕过 Sqrt 的产物。

**💜 小爱参考回答（面试标准）：**
`normalized` 的性能隐患在于它触发了定点数开方（Newton 迭代法，多轮循环逼近），这是 FixedMath 中最贵的运算之一。在帧同步的每帧循环中，如果有多个实体频繁调用 `normalized` 做方向计算，Sqrt 的累计开销就会导致帧耗时超标——这也是项目中曾经出现"追帧1"的原因。工程上的规避方式有三层：第一，能用平方值比较就不用开方值（项目中 `SqrDistance` 就是干这个的）；第二，方向向量尽量缓存，只在状态变化时重算；第三，能用 XZ 平面投影的就不要算完整的 3D 长度。这些优化的本质都是**用一次乘法换掉一次 Sqrt**。

### FixedVector3 — Q4：`#if !Server` 包围 `ToVector3()` 和 `FromVector3()` — 帧同步逻辑层能调吗？

**帅老大回答：**
没有链接服务器时会调用，接入了服务器就不会执行。

**评价：** ⚠️ 方向接近，把编译期预处理当成了运行时判断

**❌ 错误点：**
- `#if !Server` 是**编译期预处理指令**，不是运行时 `if`。打 Server 包时编译器直接把这段代码删掉，不是"不执行"，是**根本不存在于二进制文件中**。

**✅ 正确答案：**

帧同步逻辑层**不能**调用这两个方法：

1. **确定性隔离：** `ToVector3()`/`FromVector3()` 涉及 `float` (Unity Vector3)。逻辑层必须 100% 确定，一旦调了 `FromVector3` 把 float 转成 FixedVector3，不同设备的 float 可能不同 → 转出来的 FixedVector3 也不同 → MD5 脱同步。`#if !Server` 物理隔绝：Server 包编译直接报错。

2. **真正的用途：** 渲染层专用——`ToVector3()` 把 FixedVector3 → Unity Vector3 给 transform 显示；`FromVector3()` 编辑器/场景初始化用。

**💜 小爱参考回答（面试标准）：**
`#if !Server` 是一条**编译期预处理指令**，不是运行时判断。它的作用是：打 Server 包时，编译器直接把这两个方法从二进制中删除，编译都不编译。为什么需要这样？因为帧同步逻辑层要求 100% 确定性，而 `ToVector3`/`FromVector3` 涉及 Unity 的 `float`（Vector3），float 在不同平台结果不一致。如果逻辑层调了 `FromVector3` 把渲染层的 float 转回 FixedVector3，就引入了不确定性。`#if !Server` 物理隔绝了这个风险——Server 包编译直接报错，确保逻辑层永远碰不到 float。这两个方法的真正用途是：`ToVector3` 给客户端 MonoBehavoiur 更新 transform 显示，`FromVector3` 给编辑器工具做场景初始化，都属于渲染层，不是逻辑层。

### FixedVector3 — 补充讲解：追帧 1 的原理

**帅老大提问：** "模拟耗时"没太懂，是指预测时某帧实体计算太多导致帧消耗过大触发追帧吗？

**🦉讲解：**

帧同步时钟模型：
```
Unity 渲染帧（16.6ms @ 60fps）
  └── 执行 N 个逻辑帧（每个 33ms @ 30fps 逻辑帧率）
```

**模拟耗时** = 一个逻辑帧的全部计算（物理积分 + 状态机 + 快照保存 + MD5），不限于预测。

**追帧逻辑：** 上一帧 Unity 渲染时间片用完了，欠了 1 个逻辑帧没执行 → 下一帧补跑 → ⚡追帧 1。Sqrt 累积是帮凶——比加减乘除慢一个数量级。

**帅老大的理解修正：**
- "预测的时候" → 不是，**每帧逻辑模拟**都有这个开销
- "实体计算太多" → 不是数量问题，是**单个实体调了重计算（Sqrt）累积**

项目只追 1 帧说明：大多数帧在预算边缘，偶发超标。阶段2加更多系统后会加剧。

**💜 小爱参考回答（面试标准）：**
帧同步的"追帧"本质是逻辑帧和渲染帧的步调不一致。正常情况一个 Unity 渲染帧内执行完预定数量的逻辑帧即可，但如果某一帧的逻辑计算量突增（比如多个实体同时调了 FixedMath.Sqrt），导致逻辑帧耗时超过了渲染帧的预算，就"欠账"了——欠下的逻辑帧必须在后续渲染帧里补跑。这就是追帧。追 1 帧说明大多数情况下刚好在预算边缘，少一两次 Sqrt 调用就能避免。真正的解法不是优化 Sqrt 算法本身，而是用平方值比较替代开方（项目中 SqrDistance 已在做这件事）。
