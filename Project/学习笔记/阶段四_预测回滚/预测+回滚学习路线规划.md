## 4.1 为什么需要预测+回滚（认知建立）

### 核心问题

阶段三的 Demo 中，200ms 延迟下——

```
P1 按左键          P2 画面               200ms后 P2才看到
  ↓                  ↓                       ↓
P1: "我的方块左移"  P2: "P1怎么还在原地？"   P1突然出现在左边

问题：P2 看到的 P1 位置总是过时的（落后200ms）
```

### 要理解的概念

| 概念 | 比喻 | 和帧同步的关系 |
|------|------|-------------|
| **本地预测** | "不等对方回信，先按自己的想法走" | 收到自发的 Input → 立刻执行，不等服务器确认 |
| **服务器确认** | "对方收到信了，说没错" | 服务器回包说"你帧100的Input我收到了，是正确的" |
| **回滚** | "走错了？退回到岔路口重走" | 预测错了（服务器说不对）→ 退回到正确帧重新执行 |
| **快照** | "在每个路口拍照留念" | 保存每个逻辑帧的全部状态，回滚时用来恢复 |

### 阶段三和阶段四的关键区别

```
阶段三——无预测（纯等服务器）:
  帧100: 发Input → 等服务器转发 → 收到后才执行 → 已经晚了100ms

阶段四——有预测:
  帧100: 发Input → 立刻本地执行 → 同时等服务器确认
        （用户立即看到反馈！）
```

## 4.2 本地预测

### 什么是本地预测

```
现有框架（无预测）：
  ReadInputs() → [本机Input, 网络队列Input]
       ↓
  等网络队列里有数据 → 才执行 → 有延迟

加入本地预测：
  ReadInputs() → [本机Input, 预测的对方Input]
       ↓
  不等网络！先假设对方上一帧Input和这一帧一样
  如果对方实际Input到了 → 替换预测值
```

### 第一个改动——最简预测

```
预测规则极其简单：
  "对方上一帧按了↑ → 这一帧大概率还是↑"
  
  网络队列空 → 用上一帧的Input
  网络队列有数据 → 用真实Input → 更新"上一帧Input"
```

### 效果对比

```
无预测: 每帧都要等网络 → 每帧延迟 200ms
有预测: 网络没数据 → 用上一帧 → 画面不卡顿！
        (网络数据到了 → 替换 → 纠正)
```

### 关键问题

| 问题 | 回答 |
|------|------|
| 预测一定会对吗？ | ❌ 不——玩家可能突然转向 |
| 预测错了怎么办？ | → 需要回滚机制（4.4） |
| 哪些状态可以被预测？ | 玩家的输入可以，服务器事件不行 |

## 4.3 快照系统

有了预测，必须准备"后悔药"——就是快照。

```
帧同步引擎每帧都在跑逻辑（ExecuteOneFrame）
   → 方块的位置每秒都在变化
   → 如果预测错了，必须能回到"错误发生之前"的状态
   → 因此，必须保存"中间状态"
```

### 快照是什么

```
帧 100: 保存 → 方块1位置(100,50)  方块2位置(200,30)
帧 101: 保存 → 方块1位置(102,50)  方块2位置(198,30)  
帧 102: 保存 → 方块1位置(104,48)  方块2位置(196,30)
           ⋮
帧 105: "服务器说帧101的Input不对！"
             ↓
        回退到帧100的快照 → 用正确的Input重新执行帧101~105
```

### 快照要存什么

```
对当前 Demo 而言：
  - 方块1 的坐标 (FixedInt x, FixedInt y)
  - 方块2 的坐标 (FixedInt x, FixedInt y)
  - 当前 frameID

共 5 个 int → 20 字节/帧 × 256 帧 → 约 5KB
```

### 和现有 FrameBuffer 的关系

```
FrameBuffer (存Input)             快照系统 (存State)
  ┌────┬────┬────┬────┐           ┌────┬────┬────┬────┐
  │I100│I101│I102│I103│           │S100│S101│S102│S103│
  └────┴────┴────┴────┘           └────┴────┴────┴────┘
  
  存"因"：每帧的Input                 存"果"：每帧执行后的状态
  FrameEngine 有现成的                新加——阶段四核心
```

## 4.4 回滚纠正

回滚是"本地预测"的修正机制——这是整个阶段四最难的部分。

### 场景演示

```
场景：P1 原本在向左走，第100帧突然按了"右"

P1 客户端：
  帧100: 按右 → 本地预测执行 → 方块向右移了  ← 先错了！
  帧101: 按右 → 本地预测执行 → 方块继续右移
  帧102: 服务器回包确认:"帧100的Input=右"
       ↓                                    
  检查：和本地预测的一样吗？一样！✅ 不用回滚

另一场景：P2 (网络延迟) 突然转向
  P1 预测P2帧100还是"上" → 执行了
  帧102: 服务器说"P2帧100的Input=右"
       ↓
  检查：和本地预测的不一样！❌ 预测错了！
       ↓
  回滚：
    ① 回到帧99的快照 ← 从快照恢复
    ② 用已知正确的Input集重新执行帧100~102
    ③ 跳到最新的正确状态 ← 玩家感觉"突然纠正了"
```

### 回滚三步曲

```
第1步：找到"错误帧"
   服务器说"帧100的Input不对"
         ↓
第2步：回到帧99的快照
   state = snapshots[99]
         ↓
第3步：用「确认正确的Input」重新执行帧100~当前
   for (int i = confirmedFrame; i <= currentFrame; i++) {
       inputs[0] = 真实Input（来自服务器确认）
       inputs[1] = 真实Input或本地预测
       ExecuteOneFrame(inputs);
   }
         ↓
  现在状态完全正确了！✅
```

### 和阶段三 Demo 的连接

| 阶段三现有机制 | 阶段四新增 |
|-------------|----------|
| `FrameEngine.ExecuteOneFrame()` | 回滚时重新调用它 |
| `OnRequestInput` 拉取输入 | 回滚时从"已确认Input列表"拉 |
| `MarkRead` 标记已消费帧 | 回滚时只滚未确认的帧 |

### 关键的认知转变

```
阶段三：MarkRead(103) → "帧100-103不用再看了"
阶段四：MarkRead(103) → "帧100-103已被服务器确认，不会回滚了"
                      （只有「已确认」的帧才能 MarkRead！）
```
