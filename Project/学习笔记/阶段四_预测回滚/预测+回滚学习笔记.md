## 4.1 为什么需要预测+回滚

### 阶段三的延迟问题

阶段三的联机 Demo 中，每个输入要经过服务器中转。假设延迟 200ms：

```
时间轴(ms):    0      100     200     300     400     500

P1按键→       [按右]
服务器收到→            [收到→转发]
P2收到→                              [右] 
                                                [P2画面上P1右移]

P1早就按了右！！！P2过了200ms才看到P1在右移
这200ms里，P2画面里的P1在"原地踏步"
```

**核心矛盾：** 帧同步保证逻辑一致、最终位置一致，但不保证画面实时一致。延迟导致 P2 看到的 P1 位置总是过时的。

### 解决思路

**核心思想就一句话：不等，先跑。**

```
帧 100:
  P1键盘输入
  ↓
  ↙↘
 ↓  ↘
 ↓   →发服务器
 ↓
 ↓  本地立刻执行
 ↓  "P1右移了"
```

对 P1 自己来说——预测容易，自己按了什么自己知道，立刻执行 → 零延迟。
对 P2 来说（预测对方）——难！P1下一帧会按什么？猜——猜错了就要回滚纠正！

## 4.2 本地预测

### 阶段三的 ReadInputs（无预测）

```csharp
if (isNetworkMode)
{
    inputs[myIndex] = ReadMyInput();
    
    if (TryGetRemoteInput(out FrameInput remoteInput))
        inputs[otherIndex] = remoteInput;    // 有数据 → 用真实Input
    else
        inputs[otherIndex] = default;        // 没数据 → 空输入！等于没动
    
    return inputs;
}
```

**问题：** `else` 分支返回 `default`（空输入），等于对方没动，但对方其实可能一直在按方向键。

### 加入本地预测后

```csharp
// 新增：记录对方上一帧的Input
FrameInput _lastRemoteInput = default;

FrameInput[] ReadInputs()
{
    if (isNetworkMode)
    {
        inputs[myIndex] = ReadMyInput();
        
        if (TryGetRemoteInput(out FrameInput remoteInput))
        {
            inputs[otherIndex] = remoteInput;
            _lastRemoteInput = remoteInput;   // ← 记住这一帧
        }
        else
        {
            // 没数据 → 预测：假设对方和上一帧一样！
            inputs[otherIndex] = _lastRemoteInput;
        }
        
        return inputs;
    }
}
```

**改动只有 2 行：**
1. 加了一个 `_lastRemoteInput` 字段
2. `else` 分支里用上一帧Input替代 `default`

### 效果对比

```
无预测（阶段三）:
  帧100: P1按右 → 本地执行右移 → 等P2的Input → 没数据→ default
          → "P2没动" → 实际P2一直在按上！
  帧102: P2的Input到了("上") → 才看到P2在往上走 → 画面突然跳变
  
有预测（阶段四）:
  帧100: P1按右 → 本地执行右移 → P2没数据 → 预测: P2还在按上
          → "P2在往上走"（假设正确）
  帧102: P2的Input到了("上") → 和预测一样！
          → 画面平滑，不用任何纠正 ✅
```

### 小结

```
本地预测就一句话：
  "网络上一个人的Input还没到？先用他上一帧的顶着"
  → 大部分时间预测是对的（玩家不会每帧变方向）
  → 预测错的时候 → 需要回滚机制兜底
```

## 4.3 快照系统

### 什么是快照

```
快照 = 在某个时刻，把游戏世界的"全部状态"复制一份存起来

对我们 Demo 来说：
  方块1位置(x, y) + 方块2位置(x, y) + 当前帧号
  = 5 个 int 值（帧同步的优点：状态极其精简！）
```

### 为什么需要快照

```
没有快照的世界：
  "服务器说帧102预测错了……但我已经执行到帧105了"
  "帧101的方块在哪？……我不知道啊！"
  "完蛋，没法回退了"

有快照的世界：
  每帧拍照 → 帧103发现帧102错了 → 取出帧101的快照
  → 用正确Input重新执行帧102 → 得到正确状态
```

### 快照数据结构

```csharp
// 新增文件: FrameSnapshot.cs

public struct FrameSnapshot
{
    public int frameID;           // 这是哪一帧的快照
    
    // 方块1的状态
    public FixedInt player1X;
    public FixedInt player1Y;
    
    // 方块2的状态
    public FixedInt player2X;
    public FixedInt player2Y;
    
    // 如有更多游戏对象，继续加字段
}

// 快照缓冲区（和 FrameBuffer 一样的环形设计）
public class SnapshotBuffer
{
    private FrameSnapshot[] _snapshots;
    private int _capacity;
    
    public SnapshotBuffer(int capacity = 256)
    {
        _capacity = capacity;
        _snapshots = new FrameSnapshot[capacity];
    }
    
    public void AddSnapshot(FrameSnapshot snapshot)
    {
        int index = snapshot.frameID % _capacity;
        _snapshots[index] = snapshot;
    }
    
    public FrameSnapshot GetSnapshot(int frameID)
    {
        int index = frameID % _capacity;
        return _snapshots[index];
    }
}
```

### 快照怎么拍

在 `GameController.cs` 的每帧执行完后拍一张：

```csharp
void OnFrameUpdate()
{
    HandleInput();
    ExecuteOneFrame();
    
    // 新增：执行完后拍快照
    if (isNetworkMode)
    {
        var snapshot = new FrameSnapshot
        {
            frameID = currentFrame,
            player1X = player1.x,
            player1Y = player1.y,
            player2X = player2.x,
            player2Y = player2.y,
        };
        _snapshotBuffer.AddSnapshot(snapshot);
    }
}
```

### 快照存储量分析

```
每帧: 5 × 4字节 = 20字节
环形缓冲: 256帧
最大占用: 256 × 20 = 5,120 字节 = 5KB

对比 FrameBuffer（存Input）:
  每帧: uint × 2 = 8字节
  256帧: 2KB

两者加起来才 7KB —— 帧同步的极致轻量！
```

### 快照 vs FrameBuffer 的协作关系

```
FrameBuffer（存Input — 因）         SnapshotBuffer（存State — 果）
  ┌────┬────┬────┬────┐              ┌────┬────┬────┬────┐
  │I100│I101│I102│I103│              │S100│S101│S102│S103│
  └────┴────┴────┴────┘              └────┴────┴────┴────┘
      │                                  │
      │   回滚时一起用：                   │
      │  ① 从Snapshot取S101              │
      │  ② 从FrameBuffer取I102,I103      │
      └──→③ 重新执行 → ④ 得到正确状态    │
```

### FrameBuffer 在阶段四的新含义

```
阶段三：FrameBuffer → "存输入用的环形缓冲"
阶段四补充：FrameBuffer 还是"回滚时的重放源"

所以 FrameBuffer 里的帧不能随便 MarkRead 掉：
  MarkRead(101) = "帧101已被服务器确认 → 不会再回滚到它之前了"
```

## 4.4 回滚纠正（核心算法）

### 关键帧概念

```
confirmedFrame  — 已确认帧
  服务器说："帧100-105的Input全部收到，是正确的"
  → <=105的帧永远不会再被回滚
  → 可以放心 MarkRead 掉

predictedFrame  — 预测帧
  帧106~110，本地已经执行了，但服务器还没确认
  → 随时可能被回滚

currentFrame    — 当前帧（正在执行到哪了）
  帧111，引擎正在跑这一帧
```

### 回滚什么时候触发

服务器回包结构在阶段四加了确认信息：

```
阶段三: { playerInput: 0x0100 }
阶段四: { playerInput: 0x0100, confirmedFrame: 105 }
                                ↑ 新增：确认帧号
```

**客户端收到回包后比对：**

```csharp
void OnServerPacket(Packet packet)
{
    remoteInputQueue.Enqueue(packet.playerInput);
    
    int serverConfirmed = packet.confirmedFrame;
    
    if (serverConfirmed > _lastConfirmedFrame)
    {
        // 检查 lastConfirmedFrame+1 到 serverConfirmed 之间的帧
        // 本地预测的和服务器确认的是否一致？
        CheckPrediction(serverConfirmed);
        _lastConfirmedFrame = serverConfirmed;
    }
}
```

### CheckPrediction — 回滚触发判断

```csharp
void CheckPrediction(int serverConfirmed)
{
    for (int i = _lastConfirmedFrame + 1; i <= serverConfirmed; i++)
    {
        FrameInput serverInput = _confirmedInputs[i];     // 服务器确认的
        FrameInput localInput = _localPredictedInputs[i];  // 本地预测的
        
        if (serverInput._raw != localInput._raw)
        {
            // ❌ 预测错了！触发回滚
            Rollback(i - 1);  // 回到确认帧的上一帧（安全位置）
            return;
        }
    }
    // ✅ 全部正确，不用回滚
}
```

### Rollback 三步曲

```csharp
void Rollback(int safeFrame)  // safeFrame = 最后一个确定的帧
{
    // ──── 第一步：从快照恢复状态 ────
    FrameSnapshot snapshot = _snapshotBuffer.GetSnapshot(safeFrame);
    RestoreState(snapshot);
    
    // ──── 第二步：用确认正确的Input重跑 ────
    for (int i = safeFrame + 1; i <= _currentFrame; i++)
    {
        FrameInput confirmed = _confirmedInputs[i];
        FrameInput inputToUse = confirmed._raw != 0 
            ? confirmed : _localPredictedInputs[i];
        
        // 构造 inputs[2] 数组 → 重新执行
        ExecuteOneFrame(inputs);
        
        // 重新拍快照（覆盖旧的错误快照）
        TakeSnapshot(i);
    }
    
    // ──── 第三步：继续跑后续帧（用预测） ────
    // 状态已纠正，继续从 _currentFrame + 1 正常跑
}
```

### 完整回滚链路图

```
时间轴：

  帧100 ── 帧101 ── 帧102 ── 帧103 ── 帧104 ── 帧105 ── ...
    │         │         │         │         │
  拍照S100   拍照S101  拍照S102  拍照S103   ❌ 错了！
                                              │
                    ┌─────────────────────────┘
                    ▼
          回滚三步曲开始：
          
          ① 从快照取S103 → 方块回到帧103结束时的状态
          ② 用已确认的Input重跑帧104 → 正确位置
          ③ 继续跑帧105、106... → 回到正常状态 ✅
```

### MarkRead 在阶段四的含义转变

```
阶段三：MarkRead(103) = "帧103不用再看了"
阶段四：MarkRead(103) = "帧103已被服务器确认，不会回滚了"
                      = "可以安全地把帧103之前的快照都清掉"
                      
       安全边界 ≠ 消费指针
       ≤ MarkRead 的帧 → 永不会被回滚
       > MarkRead 的帧 → 随时可能被回滚
```

### 算法总结

```
┌────────────────────────────────────────────────────────┐
│  每帧正常执行（已加预测）：                              │
│    ① ReadInputs → 自己的Input + 预测/真实的对方Input    │
│    ② 本地执行 → 方块移动                                │
│    ③ 拍快照 → 存当前状态                               │
│    ④ 发Input + 本地帧号 → 给服务器                      │
│                                                          │
│  收到服务器回包时：                                      │
│    ① 更新 confirmedFrame                                │
│    ② 遍历 confirmedFrame 之间的帧                       │
│    ③ 有预测错误？→ 触发回滚                             │
│                                                          │
│  回滚：                                                  │
│    ① 快照恢复到 safeFrame                                │
│    ② 从 safeFrame+1 重跑到 currentFrame                 │
│    ③ 继续后续帧                                         │
└────────────────────────────────────────────────────────┘
```

### 概念链总结

```
"发现延迟" → "预测" → "拍快照" → "发现错了" → "回滚" → "继续"
   4.1        4.2      4.3         4.4          4.4     4.2+4.4
```
