### Q18（新）：预测正确率 301/301 对吗？什么场景下会出现真正的预测错误？

**帅老大回答：**

这个问题我不清楚。预测错误我感觉可能是发送的帧，中间的帧丢失了，可能会导致帧不连续，而导致错误。

**🦉评判：** ⚠️ **40分 — 方向偏了。** TCP 是有序可靠传输——包不会丢，也不会乱序。帧号不连续的问题在 TCP 下根本不存在。

**真正触发预测错误的场景：对手按键变了，而我的预测还停留在"对手之前按的键"上。**

具体例子：对手帧100/101 按W向北走，帧102 突然松手停下。但因为 200ms 延迟（≈6帧盲区），P1 的帧102~105 远端数据还没到，只能用 W 继续预测 P2 往北走。等帧108 远端包终于到了，ResolveRemote 发现历史里帧102 标记了 isPredicted=true，预测值=W，但真实值 actualRaw=0（空）→ W≠0 → 触发预测错误。**触发条件就一个：对手的输入在盲区窗口内发生了变化。**

为什么 301/301 全对？因为测试时对手在连续移动没变向——不是代码无敌，是测试场景太简单。下次测试试试 P2 一直按 W 走，然后突然松手，就能看到红色预测错误日志。

**💜小爱参考回答（面试标准）：**
这道题考的是"预测系统在什么情况下失效"。总结：**预测错误 ≠ 网络丢包（TCP 不丢），预测错误 = 对手行为在盲区内变了，而我还在用旧值猜。** 展开来说，预测的本质是"假设对手继续做上一帧做的事"。如果对手一直按 W，这个假设是对的——301 次全对。但一旦对手改变输入（松手、换方向、从静止变移动），而新数据还在 200ms 外的路上，我这 6 帧盲区里就会用错误的旧值继续预测。等新数据到了，PredictionSystem 的验证逻辑发现 used ≠ actual → 标记错误帧 → 触发回滚。这恰恰说明预测系统在正常工作——不是 301 次验证通过就"正确无误"，而是"还没碰到变向场景所以没触发"。

### Q19：为什么 `FixedMath.Sqrt` 要用 Newton 法自己实现，不能用 `Mathf.Sqrt`？Newton 法原理是什么？

**帅老大回答：**

为什么要引入 FixedMath.Sqrt，这里主要是防止精度溢出。本身实际的数会先 ×Scale，在平方过后会出现 int 溢出的问题。Newton 平方根的原理这个我不清楚，只知道他是先转化为 long 来防止精度溢出问题。

**🦉评判：** ⚠️ **50分 — 有两个混淆需要纠正。**

**❌ 错误1：Sqrt 自己实现的原因不是"防止精度溢出"。** 那是 `FixedInt *` 乘法加 `long` 中间值解决的问题，不是 Sqrt 的原因。Sqrt 自己实现的真正原因是**确定性（Determinism）**——`Mathf.Sqrt(4)` 在 x86 上可能等于 `2.000000`，在 ARM 上可能是 `2.000001`，差 0.000001 单帧看不出来，但上千帧累积 → 两客户端完全不同。`FixedMath.Sqrt(4)` 永远是 `2000`（即 2.0），纯整数运算，跨平台永远一致。

**❌ 错误2：Newton 法原理完全不知道。** 这次需要讲懂。

**Newton 法求平方根原理（架构导师讲清楚）：**

**问题：求 √n，即 x² = n。**
**核心公式：`r_{k+1} = (r_k + n / r_k) / 2`**

直觉：猜一个初始值 r0 = n（比如求√9，猜9），然后反复迭代：
- 迭代1: r1 = (9 + 9/9) / 2 = (9 + 1) / 2 = **5**
- 迭代2: r2 = (5 + 9/5) / 2 = (5 + 1.8) / 2 = **3.4**
- 迭代3: r3 = (3.4 + 9/3.4) / 2 ≈ (3.4 + 2.65) / 2 ≈ **3.02**
- 迭代4: r4 = (3.02 + 9/3.02) / 2 ≈ **3.00003** → 接近 √9=3.0

**原理：** 如果我猜的数太大（9 > √9），那么 n/r 会太小，两者取平均就往真实值靠拢。每次迭代误差减半。

**代码里用 `long` 的原因：** `value._raw` 是 int（最大 21 亿），乘以 SCALE=1000 后最大 2 万亿——超 int 上限，用 long 保证中间值不溢出。和之前修的 FixedInt 乘法用 long 中间值是同一个道理。

**💜小爱参考回答（面试标准）：**
这题考的是帧同步中"确定性计算"的核心原则。**总结：自己实现 Sqrt 是为了跨平台确定性（整数运算永远一致），不是因为溢出；用 long 是为了防溢出（中间值保护），不是因为精度。** 展开讲：帧同步要求两端在相同输入下得出完全相同的输出。`Mathf.Sqrt` 底层依赖 float 硬件指令，x86 和 ARM 的浮点实现有微小差异（比如舍入策略不同），同一个 `(float)4.0` 开方可能得到 `2.000000` 和 `2.000001`。单帧这点差异无关紧要，但 30FPS 跑 10 分钟 = 18000 帧，每帧差一点点，累积起来两端的球员位置、球轨迹完全分叉。所以帧同步的数学库必须用纯整数实现——`FixedMath.Sqrt` 全程用 `long` 做整数除法、位移运算，在任何 CPU 上结果一模一样。**至于 Newton 法，本质是一个"猜-修正-再猜"的循环：猜大了，n/r 就小，取平均就变小；猜小了，n/r 就大，取平均就变大。每次循环误差减半，5~8 次就收敛到答案了。**
