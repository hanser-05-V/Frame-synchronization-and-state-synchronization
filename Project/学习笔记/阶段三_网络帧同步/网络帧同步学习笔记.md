## 3.1 网络世界观

### 快递比喻

把网络通信想象成寄快递——帧同步就是不断给对方寄"按键操作"的信封。

```
┌──────────┐                               ┌──────────┐
│  你(客户端A)  │  ──── 互联网 / 局域网 ────   │  朋友(客户端B) │
│              │                           │              │
│ ① 打包      │  →  FrameInput._raw(4字节)  →  │  ④ 拆包      │
│   Input→uint │      (路上可能需要 5~100ms)      │   uint→移动   │
│ ② 贴上地址   │                             │  方块动了！    │
│   IP:端口     │                            │              │
│ ③ 发出去     │                             │  ⑤ 拆信解析   │
│   Send()     │  ←  FrameInput._raw(4字节)  ←  │  Recv()      │
└──────────┘                                └──────────┘
```

### 帧同步里的"信"

```
按键(W/A/S/D) → 打包成 FrameInput._raw (uint, 4字节)
                            ↓
                    发给服务器 → 转发给对手
                            ↓
                 对手的 FrameEngine 消费这个 uint
                            ↓
                    方块按照同样的 FixedInt 逻辑移动
                            ↓
                    ✨ 轨迹完全一致！
```

### 🆚 单机 vs 联网：就改了一个输入源

```
单机 Demo:
  ReadInputs() → return [读本机键盘, 读本机键盘]
                                  ↑            ↑
                               P1的Input    P2的Input
                              （本机两者都自己控制）

联网后:
  ReadInputs() → return [读本机键盘, 读网络收到的uint]
                                  ↑            ↑
                               P1的Input    P2的Input
                              （自己控制）  （对面发来的）

FrameEngine 一行都不改！
```

### 🔑 网络世界的三个基本概念

| 概念 | 类比 | 帧同步里的角色 | 代码长什么样 |
|------|------|--------------|-------------|
| **IP** | 小区地址 | 服务器在哪台机器 | `"127.0.0.1"` / `"192.168.1.5"` |
| **端口(Port)** | 门牌号 | 服务器在哪个进程等数据 | `8888` |
| **TCP** | 顺丰快递(签收确认) | 入门联机用——保证顺序、不丢包 | `TcpClient` / `TcpListener` |
| **UDP** | 扔纸飞机(不管到没到) | 进阶用——帧同步最常用，允许丢帧 | `UdpClient` |

### 联网后完整数据流

```
                  ┌──────────── 服务器(只转发) ────────────┐
                  │                                        │
    ① 客户端A按键  │                                        │  ④ 客户端B收到
    (WASD)       │                                        │  对方的Input
       ↓          │                                        │       ↓
    FrameInput   │                                        │  "P1按了↑"
    ._raw = 0x100│ ────→ 收到A的uint ──→ 转发给B ──→     │
       ↓          │                                        │       ↓
    send(0x100)  │                                        │  recv()收到0x100
       ↓          │                                        │       ↓
    同时本地也执行 │                                        │  注入FrameEngine
    "我按了↑"    │                                        │  "P1方块向上移"
       ↓          │                                        │       ↓
    P1方块上移    │                                        │  P2屏幕上P1方块上移 ✨
                  │                                        │
                  │  ← 同时B的Input也发给A（方向相反）→      │
```

### ❓ 验收问题

> 联网后，P2 的方块为什么能在 P1 屏幕上动？
> 数据从哪来、经过了谁、最后被谁消费？

**帅老大回答（2026-07-06）：**
P1 移动过后，会向服务器发送输入信息，服务器接受完过后下发给同服务器内的所有客户端，其他客户端接受到其他玩家的输入信息后，会进行处理，所以可以看到 P1 在 P2 屏幕上运动。

**🦉架构导师评判：✅ 正确。** 数据链路完全说对了：P1按键→打包→发送→服务器→转发→P2收到→处理→P2屏幕上的P1方块动了。

## 3.2 TCP vs UDP 对比

### 一、TCP vs UDP：为什么帧同步倾向 UDP？

```
TCP（可靠但有队头阻塞）:

  发送:  数据包 A → B → C → D

  正常:  A ✓ → B ✓ → C ✓ → D ✓           全部收到，顺序正确

  丢包:  A ✓ → B ✓ → C ❌ → D ✓
                      ↑
              C 丢了！但 D 已经到了
              → TCP 说："必须等 C 重传！D 先别处理！"
              → C 重传...C 重传...
              → 终于 C ✓ → 现在才能处理 D

  后果：一次丢包阻塞后续所有包
        帧同步 30FPS 的节奏被打乱
        玩家看到的是"突然卡顿→加速→恢复正常"


UDP（不可靠但无阻塞）:

  发送:  数据包 A → B → C → D

  丢包:  A ✓ → B ✓ → C ❌ → D ✓
                      ↑
              C 丢了，D 直接处理！
              → 少一帧？无所谓——用上一帧推算就行

  后果：丢一帧无所谓，节奏不被打断
        帧同步宁可丢帧，也不接受延迟波动
```

### 二、入门为什么用 TCP 不用 UDP？

```
TCP = 打电话 — 号码一通，说什么对方就听到什么
               不用操心顺序、丢包
               适合入门：逻辑简单，跑通再说

UDP = 扔纸飞机 — 扔了不管，没收到也不告诉你
                 需要自己处理丢包重传
                 适合进阶：帧同步常用，但实现复杂
```

### 🆚 总结对比

| | TCP | UDP |
|------|------|------|
| 可靠性 | ✅ 保证送达、保证顺序 | ❌ 可能丢、可能乱序 |
| 速度 | 🐢 丢包时被阻塞 | 🚀 一直飞，不等 |
| 适用场景 | 网页、文件下载、**入门Demo** | 视频通话、**生产帧同步** |
| 代码复杂度 | 🟢 简单（Read/Write 就行） | 🟡 复杂（要自己处理丢包） |
| 帧同步为什么用它 | **入门用**——先跑通联机 | **最终目标**——不丢节奏 |

**策略**：先学 TCP 把联机跑通，逻辑跑通后后续再换 UDP。逻辑一样，只换传输层。

## 3.3 Socket 六兄弟

### Socket 是什么？

```
Socket = 一根电话线

打个电话的过程：
  你拨号(connect) → 对方接听(accept) → 说话(send) → 对方听到(recv) → 挂断(close)
```

C# 里，`TcpListener` 和 `TcpClient` 帮我们封装好了这根电话线。

---

### 服务器端三兄弟（等电话的人）

```csharp
// 老大：创建接线员，蹲在 8888 门口等
var listener = new TcpListener(IPAddress.Any, 8888);
listener.Start();  // 开始接电话

// 老二：有人来电 → 接起来 → 建立"通话专线"
var client = listener.AcceptTcpClient();  // 阻塞！一直等到有人连

// 老三：从通话专线拿到"话筒"
var stream = client.GetStream();  // 通过这个流说话/听话
```

```
listener.Start()                    listener.AcceptTcpClient()
      ↓                                        ↓
  "开门营业"                            "有人来了，接电话"
      ↓                                        ↓
  蹲在 8888 门口                        建立一条专用电话线
      ↓                                        ↓
  随时准备接                              client.GetStream()
                                            ↓
                                       "话筒给你——说话/听话都通过它"
```

### 客户端兄弟（打电话的人）

```csharp
// 老四：拿起电话，拨号
var client = new TcpClient();
client.Connect("127.0.0.1", 8888);  // 拨号：地址 + 门牌号

// 老五：拿话筒（和服务器老三一样）
var stream = client.GetStream();
```

```
TcpClient()                    Connect("127.0.0.1", 8888)
      ↓                              ↓
  "我要打电话"                    "拨号中...嘟嘟嘟..."
      ↓                              ↓
  准备拨号                      服务器接听了 → 线通了
```

### 收发兄弟（双方共用）

```csharp
// 老六-发：对着话筒说话
byte[] data = BitConverter.GetBytes(input._raw);  // uint → 4字节
stream.Write(data, 0, data.Length);               // 发送！

// 老六-收：听对方说什么
byte[] buffer = new byte[4];                  // 准备4字节的"耳朵"
int count = stream.Read(buffer, 0, 4);       // 听！（阻塞，等数据到达）
uint raw = BitConverter.ToUInt32(buffer, 0); // 4字节 → uint
```

```
发:  0x100 → [0x00,0x01,0x00,0x00] → stream.Write() → 网络 → 对面收到
收:  网络 → stream.Read() → [0x00,0x01,0x00,0x00] → BitConverter → 0x100
```

### 🗺️ 六兄弟全景图

```
服务器                              客户端
──────                              ──────
                                    new TcpClient()         ← 老四：拿起电话
TcpListener(8888)    ← 老大：接线员   │
    ↓                                ↓
listener.Start()     ← 老大：开门    Connect("127.0.0.1", 8888) ← 老四：拨号
    ↓                                ↓
AcceptTcpClient()    ← 老二：接电话   (连接建立)
    ↓                                ↓
GetStream()          ← 老三：拿话筒   GetStream()            ← 老五：拿话筒
    ↓                                ↓
stream.Read/Write    ← 老六：说话     stream.Read/Write      ← 老六：说话
```

### 🆚 对比总结

| 兄弟 | API | 谁用 | 类比 | 特点 |
|:--:|------|------|------|------|
| 老大 | `TcpListener` | 服务器 | 接线员——蹲门口等电话 | 只要一个 |
| 老二 | `AcceptTcpClient()` | 服务器 | 接起电话——建立专线 | **阻塞**，等有人连 |
| 老三 | `GetStream()` | 服务器 | 拿话筒——通话通道 | 收发都靠它 |
| 老四 | `TcpClient + Connect` | 客户端 | 拨号——主动打过去 | 要知道 IP+端口 |
| 老五 | `GetStream()` | 客户端 | 拿话筒——和服务器同一个 | 和服务器老三完全一样 |
| 老六 | `Read/Write` | 双方 | 听/说——真正干活 | **Read 阻塞**，Write 不阻塞 |

---

### 🔑 关键理解：两个阻塞点

```
AcceptTcpClient() — 没人连就一直等
     ↓
[有人连了] → 继续往下走
     ↓
Read() — 没数据就一直等
     ↓
[有数据到了] → 继续往下走
```

**这导致一个问题**：如果 Read() 在等数据，游戏画面就卡住了（因为 Unity 主线程被阻塞）。

→ **解决方案：Read() 必须跑在独立线程。** 这是 3.4 联机 Demo 里要解决的问题。

---

### ❓ 验收问题

> AcceptTcpClient() 和 stream.Read() 有什么共同点？
> 这个共同点在帧同步里会带来什么问题？怎么解决？

**帅老大回答（2026-07-06）：**
AcceptTcpClient 和 stream.Read() 都会阻塞线程，必须接收到数据才能继续运行。服务器那边是接收到了客户端的连线过后才会建立好通话专线，stream.Read() 是服务器和客户端从发送流中读取信息，直到读取到才进行下一步解析转化。都会阻塞线程，所以要把读取放入一个独立的线程。

**追问**：但是具体处理数据同步为什么不能使用协程呢？

**🦉架构导师评判：✅ 阻塞点完全说对了。**

## 补充讲解：为什么不能用协程？

帅老大这个问题问得很好。先拆开来看：

### 协程的本质

```csharp
// 协程 = Unity 主线程上的"分片执行"
IEnumerator MyCoroutine()
{
    yield return new WaitForSeconds(1f);  // 1秒后继续
    // Unity 回到这里继续执行——还是在主线程！
}
```

```
主线程时间轴:
  帧1: 执行协程第1段 → yield → 暂停
  帧2: 渲染画面 → 检测到1秒到了
  帧3: 执行协程第2段 → yield → 暂停
  
  关键：协程的所有代码都跑在主线程！
```

### stream.Read() 的问题

```csharp
byte[] buffer = new byte[4];
stream.Read(buffer, 0, 4);  // 这里会"彻底卡死"，不是"等1秒"的概念
```

```
协程 vs 阻塞的区别：

协程 yield return:         Read() 阻塞:
  主线程:"我停一下"            主线程:"我动不了了"
  渲染照常                     渲染卡死
  输入照常                     输入卡死
  ↓                           ↓
  1秒后自己回来                等到有数据为止
                           （可能是100ms，也可能是10秒）
```

**协程的 `yield` 是"主动暂停，约定时间回来"——主线程在此期间继续渲染、接收输入。**

**`Read()` 是"被卡死，不知道什么时候结束"——主线程什么都做不了。**

### 🆚 对比

```
协程：
  主线程 ──┬── 渲染 ──┬── 渲染 ──┬── 渲染 ──┬── ...
           │          │          │          │
           └── Wait ──┴── Wait ──┴── 继续 ──┴── ...
               (1秒)      (1秒)     (主线程没事)

stream.Read()：
  主线程 ──┬── Read(卡住了) ───────────── ??? ── ...
           │
           └── (不知道等多久，画面定格，按键无效)
```

**一句话：协程是"主动切走，主线程照常跑"；Read() 是"死等，主线程被绑架"。**

### 那正确做法是？

```
独立线程：
  主线程 ──┬── 渲染 ──┬── 渲染 ──┬── 渲染 ──┬── ...
           │          │          │          │
           │          │          │    [收到数据!]
           │          │          │    更新队列 ← 线程
           │          │          │          │
           │          │          │    ReadInputs()
           │          │          │    从队列取数据
           
  网络线程 ──┴── Read(阻塞) ──┴── Read(阻塞) ──┴── ...
              等100ms         等50ms
```

主线程每 33ms 从队列取一次数据（非阻塞，瞬间完成）。网络线程被 Read() 阻塞多久都影响不到主线程。

### 一句话总结

> **协程分片执行但仍在主线程，Read() 会绑架主线程。网络 IO 必须用独立线程。**
