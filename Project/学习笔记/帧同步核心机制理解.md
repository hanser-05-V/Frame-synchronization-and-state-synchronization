## 一、环形缓冲区（FrameBuffer）

### 它是什么

帧同步的"心跳图"——一列固定步长的火车铁轨。每 33ms 写入一帧 Input 数据，按序消费。

### 它怎么体现帧同步

```
❌ 普通游戏：  按键 → 直接移动方块
✅ 帧同步：    按键 → 打包成4字节Input → 写入环形缓冲 → 引擎固定步长取出 → 移动方块
                                  ↑
                        多了"缓冲层"——所有操作先存后取，统一节奏
```

### 缓冲区可视化

```
  FrameBuffer: 容量256帧，frameID % 256 定位

  🟢 绿色(已消费) = 已经被逻辑处理过的帧，方块已经移过了
  🟡 黄色(待消费) = 已写入但还在排队中，马上被消费
  ⬜ 灰色(空闲)   = 还没数据写入的空槽
```

### 网络同步的预留

单机下绿色和黄色区别不大。但到联网阶段：
- 黄色 = 等待服务器确认的帧
- 绿色 = 服务器确认后可安全消费的帧
- 黄色堆积 = 网络延迟大 → 需要追帧

## 二、录制回放（Record & Playback）

### 录制

```
R → 记录方块当前位置 → 帧号重置为0 → 每帧Input存入recordedInputs数组
    只记录"玩家做了什么"（Input序列），不记录画面
```

### 回放

```
P → 回到录制起点 → 帧号重置为0 → 逐帧喂入录制的Input
    → 相同输入驱动相同逻辑 → 轨迹完全一致 → 确定性验证通过
```

### 为什么能证明帧同步

```
相同Input序列 + 相同起点 → 相同轨迹 = 确定性成立
                                   ↓
                          这就是帧同步能工作的理论基础
```

## 三、追帧（Catch-up）

### 怎么触发

```csharp
// FrameEngine.Update() 中
while (elapsedMs - _lastLogicMs >= 33)
{
    _lastLogicMs += 33;   // 累加33ms
    ExecuteOneFrame();    // 执行一帧
    frameRun++;           // 计数
}

if (frameRun > 1)          // 一次跑了超过1帧？
    _catchupCount++;       // 记录追帧
```

触发条件：当一次 `Update()` 中 `while` 循环跑了超过 1 帧 → 触发追帧。

### 什么导致追帧

| 单机场景 | 联网场景 |
|---------|---------|
| 按 Space 暂停几秒后恢复 | 网络延迟导致帧数据积压 |
| 渲染帧率波动导致 Update 间隔变长 | 服务器回包后一次性到达多帧 |
| 切窗口后 Unity 暂停了渲染 | 重连后需要追上服务器进度 |

### 追帧的作用

```
正常：每33ms跑1帧
  Update①→帧100  Update②→帧101  Update③→帧102

追帧：一次Update跑多帧
  暂停3秒 → 损失了~90帧 → 恢复后Update里while循环一次性跑90帧
  方块瞬间跳到90帧后的位置（不会"慢放"，直接瞬移）

这就是帧同步的"赶上"机制——时间不会倒流，错过的帧用最快的速度补回来。
```

### 单机 vs 联机追帧

```
单机追帧: 暂停恢复后瞬间追帧 → 方块瞬移 → 直观
联网追帧: 网络恢复后瞬间追帧 → 其他玩家的动作"突然变快" → 本质一样
```

## 四、三个机制的关系

```
环形缓冲区 — 存放"帧数据"的容器
      ↓
录制回放   — 利用缓冲区的 Input 序列验证确定性
      ↓
追帧       — 利用固定步长机制，在时间落后时快速赶上
```

三者合在一起构成了帧同步的完整运行逻辑：

```
Input → 环形缓冲 → 引擎消费 → 游戏逻辑 → 画面
         ↑                      ↑
    录制/回放用            追帧在这里加速
```
