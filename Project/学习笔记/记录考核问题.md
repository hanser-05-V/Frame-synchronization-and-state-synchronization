## 阶段一：吃透单机代码

---

### Q1：单机项目不联网，为什么不直接用 float？

**帅老大回答：**
float 会有精度问题，根据不同设备的性能会有差异，这样就不能保证用户输入的准确性，得到的结果会有偏差。

**评价：** ✅ 通过

**补充：**
同一个 CPU、同一个 exe、同一次运行中，float 运算其实是确定的。帧同步用定点数的真正原因是**跨场景**的不确定性——IL2CPP vs Mono、x86 vs ARM、Debug vs Release——这些会导致 float 结果不同。定点数解决的是"录制的回放在任何机器上都能复现"。

**💜小爱参考回答（面试标准）：**
这道题考察对帧同步确定性的理解。先说结论：float 本身在同一个 exe、同一次运行中是确定的，问题出在跨场景。帧同步要保证录制回放在任何机器上都能完全复现，但 float 在不同编译器（Mono vs IL2CPP）、不同 CPU 架构（x86 vs ARM）、不同优化等级（Debug vs Release）下的运算结果可能有细微差异。比如 `0.1 + 0.2` 在 x86 上可能等于 `0.300000012`，在 ARM 上可能是 `0.300000015`——单帧差一点没关系，但上千帧累计起来就是完全不同的路径。定点数本质是用 int 模拟小数，不管在什么平台上 `100 + 200 = 300` 永远成立，这就是"确定性"的保障。所以帧同步不用 float 不是因为 float 本身不稳定，而是因为**跨平台跨编译器**的不确定性对帧同步是致命的。

### Q2：录制了 100 帧 Input，回放时只喂 Input 不记录碰撞。方块在第 50 帧撞墙怎么办？

**帅老大回答：**
因为记录了录制时候的开始帧位置，以及这段时间的输入，他必定是以同样的状态发生碰撞，所以也不需要记录碰撞。

**评价：** ✅ 满分

**补充：**
只存"因"（Input + 起点），不存"果"（碰撞 / 轨迹）。"果"由"因"通过确定性逻辑自然计算出来。

**💜小爱参考回答（面试标准）：**
这道题考的是帧同步"只存因不存果"的核心思想。录制时只录每帧的 Input（玩家按键），不录碰撞、轨迹等"结果"数据。为什么可以这样？因为帧同步的确定性——同样的输入在同样的初始条件下必定产生同样的输出。第 50 帧撞墙了，回放时从初始位置开始，喂同样的按键序列，到第 50 帧自然会再次撞墙，不需要单独存"第 50 帧撞墙"这个事实。这就像录了一个钢琴演奏的 MIDI（音高+节奏），回放时用同样的 MIDI 数据驱动钢琴，自然能重现同样的音乐——不需要把每毫秒的声音波形都录下来。存"果"不仅浪费存储，还会引入不一致风险（比如不同机器上碰撞检测的精度误差）。所以帧同步的核心原则就是：**只存因，不存果，因果确定，果必重现。**

### Q3：Demo 里 FrameBuffer 每写一帧立刻 MarkRead。主程说"这跟直接调 Update 没区别"——说得对不对？

**帅老大回答：**
目前单机测试下缓冲区确实几乎没有延迟就下发命令了。但是后续接入网络后便会体现出作用——客户端发送输入指令进入待缓冲区，服务器接受下发命令到缓冲区，最后客户端按照一定步长来进行处理。目前运动逻辑层和渲染层还没有分开，只是在 Update 加入了帧判断机制用于追帧。后续加入网络或功能复杂起来，分离逻辑层和渲染层分开执行，这也是帧同步和一般 Update 之间的区别。

**评价：** ✅ 正确。

**补充：**
联网后服务器的具体作用——不只是转发，权威服务器还需要对输入进行校验防止作弊，玩家挂机时服务器会做出相应措施。P2P 帧同步存在但当前主流的还是客户端+服务器模式。

**💜小爱参考回答（面试标准）：**
这道题考的是"当前设计虽然看起来多余，但为联网预留了什么"。现阶段单机下每个方块两套Input（键盘+键盘），Buffer 每帧写入后立即 MarkRead，看起来确实和直接调 Update 没区别。但关键在 MarkRead 的含义——它标记的是"已经安全可以丢弃的帧"。联网后，自己发出的 Input 需要等服务器转发回来的确认，确认之前不能 MarkRead（因为可能要回滚），所以 Buffer 里会积累"已写入但未确认"的帧。这个延迟确认的机制在单机下确实不体现价值，但架构不改就能直接跑联网——这就是预留的意义。主程说的没错，但只看单机场景忽略了这层设计意图。类似问题在系统设计中很常见：**"现在看起来多余的东西，可能是为了未来扩展预留的接口。"**

### Q4：OnRequestInput 为什么存在

**帅老大回答：**
通过 `Func<FrameInput[]>` 委托，引擎每帧拉取输入。FrameEngine 只管"给我 Input[]"，不关心来源。ReadInput 返回 FrameInput 数组传递。单机时指向键盘，联网时可换指向网络——不改引擎代码。

**评价：** ✅ 理解了委托替换机制。

**💜小爱参考回答（面试标准）：**
这道题考的是"接口解耦"的设计思想。OnRequestInput 的本质是一个 `Func<FrameInput[]>` 委托，FrameEngine 每帧回调这个委托来获取输入。FrameEngine 只关心"有没有拿到输入数组"——至于输入是来自键盘读取、网络队列还是录制回放，FrameEngine 完全不关心。这种设计的好处有三点：① 不改引擎代码就能切换输入源（单机→联网→回放）；② 输入逻辑集中到 GameController，职责清晰；③ 方便测试——测试时可以注入模拟输入数据，不需要真人按键。这其实就是"策略模式"的应用：引擎定义"拉取输入"的接口，GameController 提供不同的策略实现。**帧同步引擎只负责"按帧执行"，不负责"输入从哪里来"。**

### Q5：录制回放链路

**帅老大回答：**
recordedFrameCount 在 Debugger 中增加，Controller 执行完一帧同步调用 Debugger 更新。按 R 开始记录，初始为 0。playbackFrame 递增，当超过记录的帧数则回放结束。

**评价：** ✅

**补充：**
两个计数器都在 `FrameDebugger.UpdateFrame()` 中递增，被 `GameController.ReadInputs()` 和 `OnFrameUpdate()` 读取来判断回放结束。

**💜小爱参考回答（面试标准）：**
录制回放是帧同步确定性的验证手段。录制时，每帧所有玩家的 Input 被追加到 `recordedInputs` 列表，同时 `recordedFrameCount` 递增。回放时，引擎帧号重置为 0，`playbackFrame` 从 0 开始逐帧读取录制列表中的 Input 喂给 FrameEngine——录制时第 N 帧是什么 Input，回放时第 N 帧就喂什么 Input。因为帧同步的确定性，同样的 Input 序列必定产生同样的游戏过程，所以回放能精确复现录制时的画面。这里的关键是"因果对应"——录的是因（Input 序列），回放自然还原果（游戏过程）。如果回放结果和录制不一样，说明帧同步的确定性被破坏了，这就是用录制回放来验证帧同步是否正确的原理。**录制回放 = 帧同步确定性的"核酸检测"。**

### Q6：追帧机制深入

**帅老大回答：**
采用 for 循环一轮跑完就不跑了，当有玩家有网络延迟便会漏掉信息不能同步。追帧瞬间移动是帧同步的设计就是这样的，当一方客户端卡顿恢复后，会进行追帧，执行帧操作，一直到追上目前的帧为止。

**评价：** ✅ 正确。用 for 确实会漏帧；瞬移是设计如此，不是 Bug。

**💜小爱参考回答（面试标准）：**
追帧机制是帧同步应对"瞬时数据积压"的策略。当客户端卡顿后恢复（或联网时服务器积压了一批 Input），引擎的 Update 检测到时间差超过单帧间隔，会进入 while 循环一次性执行多帧。比如卡了 300ms（30FPS 下约 10 帧），while 循环会连续执行 10 次 `ExecuteOneFrame`。**这意味着逻辑层一下子跳过了 10 帧，画面直接跳到 10 帧后的位置——这就是"瞬移"的原因。** 瞬移不是 Bug，而是帧同步的设计选择：帧同步保证最终位置一致，不保证中间过程的平滑过渡。相比之下，状态同步会把中间状态也同步过来，但帧同步为了不引入额外同步开销，选择了"追帧瞬移"。**帧同步的思路是：与其渲染一个错误路径让用户看到，不如直接跳到正确位置。**

### Q7：定点数精度/溢出

**帅老大回答：**
Scale=1000 用于去除小数影响，保留 3 位小数。相乘使用同余原理除以 Scale。

**评价：** ✅ 思路对，需注意溢出细节。

**补充：**
- `a._raw * b._raw` 在 int 空间可能溢出（50000×50000=2,500,000,000 > int.MaxValue）
- 正确写法应用 `long` 中间值：`(int)((long)a._raw * b._raw / SCALE)`
- "同余原理"不适用——这里不是取模，是两个 ×1000 的数相乘 = ×1,000,000，除 1000 恢复 ×1000 标度

**💜小爱参考回答（面试标准）：**
FixedInt 用 `int _raw` 表示实际值的 1000 倍，比如 `1.5` 存为 `1500`。加法减法直接对 `_raw` 加减即可，但乘法有个陷阱：`1.5 × 2.5` 期望结果是 `3.75`，存为 `3750`。但计算时 `(1500 × 2500) / 1000 = 3750`，中间步骤 `1500 × 2500 = 3,750,000` 在 int 范围内（最大 ~21 亿），但如果两个数更大——比如 `50000 × 50000 = 2,500,000,000`，已经接近 int.MaxValue 的 `2,147,483,647`，再大一点就会溢出变成负数。**正确的做法是乘法用 `long` 做中间值：`(int)((long)a._raw * b._raw / SCALE)`。** 很多新手写定点数时会忽略这个溢出问题，导致"某些数值下结果突然变负数"的 bug，而且不是每次必现——只有数值大到一定程度才触发，非常难排查。这也是为什么面试中经常会追问"定点数乘法的溢出考虑"。另外帅老大说的"同余原理"不太准确，这里不是取模，而是"放大→相乘→缩小"的标度变换。

### Q8：环形缓冲深挖 — 256够用吗？帧号溢出？600帧追帧？

**帅老大回答：**
256容量一次性推600帧过来，会在while循环中不断检测然后按帧执行追帧。连续性检测可以通过，只要不是跳跃执行帧就不会出问题。

**评价：** ⚠ 80分

**补充：**
追帧时**生产=消费=1帧**，每一帧是先写入→立即执行→立即MarkRead，被覆盖的槽位都是已消费完的旧帧。256够不是因为数字大，而是因为边写边消费。

如果600帧先全部写入再执行，后面的帧会覆盖还没消费的前面帧——那才会出问题。

关于帧号溢出：`_currentFrame` 用 `int` 存储，int.MaxValue ≈ 1,970 年的帧数据。真正的帧同步游戏每局比赛开始帧号归零。`MarkRead` 用 `if (frameID > _lastReadFrame)` 防住了负帧号。

**💜小爱参考回答（面试标准）：**
256 帧够不够用，核心在于"怎么消费"。如果写一帧消费一帧（单机模式），256 帧约 8.5 秒的数据量怎么都够。追帧时也是一边消费一边写入——while 循环每执行一帧就写一帧，被覆盖的槽位都是已经消费完的旧帧。帧号溢出方面，`_currentFrame` 用 int 存可以跑到约 20 亿帧，30FPS 下大约能跑 2 年才溢出，而且一局比赛结束后帧号归零，所以实际项目不会遇到。真正要注意的是 **MarkRead 防住负帧号**——`MarkRead(frameID - 4)`，如果 frameID=0 时 frameID-4=-4，代码里有 `if (frameID > _lastReadFrame)` 的保护才不会错误标记。关于"600帧一次性写入"，如果先写 600 帧再执行，因为环形缓冲只有 256 槽，后面的帧会覆盖前面的——但 Demo 里不会出现这种情况，因为每一帧都是"先写入一帧→立刻执行一帧→MarkRead一帧"，消费速度 >= 生产速度，256 永远够用。**256 够不是因为数字大，是因为"边写边消费"这个工作模式。**

### Q9：MarkRead延迟4帧 — 改成0会怎样？（联网方向评判）

**帅老大回答（联网方向）：**
改成0游戏逻辑还是能正常运行，只是发生卡顿过后，会导致没有缓冲带，信息会丢失掉，导致客户端之间会出现不同步现象。

**评价：** ✅ 85分 — 联网方向正确

**补充：**
联网后 MarkRead 的真正含义——帧写入→本地预测执行→等待服务器确认。服务器回包确认后 MarkRead，这些帧才安全。未确认的帧不能被 MarkRead，可能被回滚。

帅老大的直觉完全对——"没有缓冲带"="没有等待确认的窗口期"；"信息丢失"="未确认帧被标记为已消费后无法回滚"；"不同步"="没有可退的快照"。

**💜小爱参考回答（面试标准）：**
MarkRead(4) 的本质是"延迟4帧再确认消费"——帧写入后不立即 MarkRead，等 4 帧后再标记。这个延迟在单机下只是一个视觉缓冲效果，但在联网场景下成为"等待服务器确认的安全窗口"。联网后逻辑是这样：客户端发出帧 N 的 Input 后，还不确定服务器是否收到——如果服务器丢包了需要重传，这期间帧 N 的数据不能被丢弃。MarkRead 标记的位置就是"已确认安全"的位置，只有 <= MarkRead 的帧才能被放心丢弃。如果把 MarkRead 改成 0（写入即丢弃），相当于"刚发出去就标记为已消费"，如果网络延迟导致服务器还没收到，客户端就没有可以回滚的数据备份了——这就是帅老大说的"没有缓冲带"、"信息丢失"、"不同步"三个连锁后果。**MarkRead 的延迟值 = 你愿意为网络抖动预留的缓冲时间，太长增加内存，太短无法容忍波动。**

### Q10：分配机制

**问题：** 客户端 1 先连服务器，客户端 2 后连。为什么客户端 1 只能控制自己的 P1，客户端 2 只能控制自己的 P2？

**帅老大回答：**
在读取输入时候，根据加入服务器的前后，目前是根据这个得到 playerIndex。后续读取输入时候，会根据 playerIndex 来采用不同的读取输入方式，这样来区别输入，另外一个的输入从网络端进行读取。后续都是 exe 时候还需要实际区分出 ID。

**评价：** ✅ 通过

**补充：**
```
客户端1 (playerIndex=0):
  inputs[0] = ReadP1Input()     ← 自己读键盘
  inputs[1] = 从网络队列取       ← 对方Input

客户端2 (playerIndex=1):
  inputs[0] = 从网络队列取       ← 对方Input
  inputs[1] = ReadP2Input()     ← 自己读键盘
```
两个客户端的 FrameInput[2] 完全相同 → 帧同步成立。FrameEngine 不关心 Input 来自键盘还是网络。

**💜小爱参考回答（面试标准）：**
分配机制的关键是"每个客户端创建两个方块但只操控一个"。服务器按连接顺序分配 `playerIndex`——先连的是 0，后连的是 1。在 ReadInputs 中，`playerIndex=0` 的客户端把自己的键盘输入填入 `inputs[0]`，从网络取对方填入 `inputs[1]`；`playerIndex=1` 的客户端反过来。这样两个客户端各自最终产出的 `FrameInput[2]` 数组是完全一致的，FrameEngine 消费这个数组时看到的就是同样的输入——帧同步的基础就成立了。这就是 Q4 里"OnRequestInput 不关心输入来源"的具体体现：**引擎看到的是同样的 inputs[]，不管 inputs[0] 是来自键盘还是网络。** 如果后续两个都是 exe，就不能用 `Application.isEditor` 来区分了，需要通过命令行参数或者配置文件来指定 localID。

### Q11：TCP vs UDP

**问题：** 帧同步最终目标是跑 UDP，为什么先跑 TCP？

**帅老大回答：**
TCP 相较于 UDP 来说链接更加稳定，步骤也相对简单，每一步都有确切的监听。UDP 是面向无连接的，直接发送消息，延迟低但是不稳定。在强调及时性对抗的游戏，UDP 使用比 TCP 更高。现在还在项目初期，先使用稳定的 TCP 测试功能，后续更进优化为 KCP，结合了 TCP 和 UDP，在消耗一定带宽的前提下，提高 TCP 的连接速度，防止出现和刚才一样延迟导致的不同步情况。

**评价：** ✅ 通过

**补充：**
TCP 有队头阻塞——丢一包后面都得等。帧同步中，这导致 Input 队列被打断，30FPS 的节奏乱掉。UDP 丢了不管，少一帧用上一帧推算就行，帧同步宁可丢帧也不接受延迟波动。

KCP 是基于 UDP 的可靠传输协议，在牺牲一定带宽（多发一些 ACK）的前提下，比 TCP 快 10-30%。它保留了 UDP 的无阻塞特性，同时自己实现重传保证最终一致性。帅老大提到了 KCP，说明对"生产级帧同步用什么传输层"有清晰的认知。

**💜小爱参考回答（面试标准）：**
这题考的是"为什么工业界选 UDP，但入门教学选 TCP"。TCP 的队头阻塞（Head-of-Line Blocking）是帧同步最致命的问题——TCP 保证按序到达，如果丢了一包，后续所有包都要等重传，哪怕后面的包已经被接收到了也只能卡住。在帧同步场景中，这意味着第 N 帧的 Input 丢了，第 N+1、N+2 帧的 Input 哪怕已经到了也不能处理，30FPS 的稳定节奏被打断。UDP 不保证顺序和可靠性——丢了就丢了，帧同步可以用上一帧的 Input 替代丢帧，宁可丢帧也不接受延迟波动。但 UDP 需要自己实现可靠性（KCP 就是在 UDP 上自己管重传和顺序），实现复杂度远高于 TCP。**入门先用 TCP 跑通联机逻辑，等理解了帧同步的网络模型后再换 UDP/KCP——逻辑层代码完全不需要改，只换传输层。** 帅老大提到了 KCP，说明对生产级方案有认知：KCP 通过多发 ACK 换取比 TCP 快 10-30% 的传输速度，牺牲带宽换延迟。

### Q12：延迟与帧同步

**问题：** 200ms 延迟下，两个客户端之间逻辑同步吗？画面同步吗？帧同步保证了什么、不保证什么？

**帅老大回答：**
逻辑是保持同步的，只要服务器正常接受到、正常下发就没有问题，只是会根据延迟波动来导致下发时段不同问题，客户端接受到输入延迟而已。目前还没有做预测，画面实时展示可能会不同步，但是最终位置肯定是同步的。

至于为什么不是瞬移，是因为延迟还没有达到。瞬移是因为客户端在一瞬间接受到了大量的输入信息，需要疯狂追帧。200ms 下，保证输入一致、运动轨迹一致、最终结果一致，但是目前不能保证画面实时运动是一致的。

**评价：** ✅ 通过 满分

**补充：**
帅老大完全说透了帧同步在这个场景下的边界：

```
逻辑同步（frameID 100 的 Input 两边相同）       ✅ 帧同步保证
运动轨迹一致（相同 Input→相同 FixedInt 计算）   ✅ 帧同步保证
最终位置一致（执行完所有帧后位置相同）           ✅ 帧同步保证
画面实时一致（同一时刻两边看到的位置相同）       ❌ 帧同步不保证——这是预测+回滚解决的问题
```

为什么不是瞬移——200ms 延迟下积压约 6 帧，while 循环一次消费 6 帧只需要 ~200ms，和渲染间隔几乎同步，所以看起来是"流畅地延迟跟上"而不是"瞬间追上"。要看到明显瞬移需要更大延迟（如 500ms）积压 ~15 帧。帅老大的理解完全正确。

**💜小爱参考回答（面试标准）：**
这道题的满分关键在于区分"帧同步保证什么、不保证什么"。① 逻辑同步 —— FrameEngine 保证了同 frameID 下两边接收到的 Input 一致，这由网络层保证，帧同步必保。② 轨迹一致 —— 同样的 Input 经过同样的 FixedInt 定点计算，方块每一步的移动量相同，累计路径相同，帧同步必保。③ 最终位置一致 —— 执行完 N 帧后两边方块的位置完全一致，这是"逻辑同步+轨迹一致"的必然结果，帧同步必保。④ 画面实时一致 —— 第 100ms 时 P1 看到的 P2 在第 100ms 的状态，和 P2 自己看到的自己在第 100ms 的状态，这两个画面不一定一样，因为 P1 看到的是 P2 100ms 前的状态（单向延迟）。**帧同步不保证这个，这也是为什么需要阶段四的预测+回滚。** 另外关于"为什么不是瞬移"——200ms 延迟压约 6 帧，while 追帧只花了约 200ms 就跑完了，几乎和正常渲染间隔同步，所以看起来不是"瞬跳"而是"流畅地追上"；如果 500ms 延迟积压 15 帧，while 跑 15 帧需要约 500ms，就会看到明显瞬移。

### Q13：本地预测解决什么问题

### Q14：回滚三步曲

---

#### 子问题①：DoRollback 全过程描述

**问题：** 用自己的话描述 DoRollback 全过程——方块怎样从错误状态"恢复正确位置"的？

**帅老大回答：**
全过程的回滚需要 GameController（控制器）、FrameSnapshot（快照缓冲区）、FrameBuffer（帧缓冲区状态）、PredictionSystem（预测系统）几个脚本进行协作。

整体调用链路是：预测系统内含一个队列和字典，以及初始阈值。初始几帧的预测不进行检测（避免初始无限回滚）。当记录帧超出预置阈值（5帧）后，便从队列弹出帧，对应查字典得出值，再和在控制器调用位置传入的值进行比较。如果一致就是预测正确，更新最后记录指针。如果控制器没有传入真实值，那就以上一次输入来进行预测（和前面初始5帧一样）。如果值不对，预测系统会更新错误帧的记录位置和对应的正确值（标记有待处理的回滚）。当控制器对应执行到检测回滚时，便触发回滚。

回滚时，先通过缓冲区快照恢复状态，最后再重新执行当前帧。本地的输入从缓冲区读，远方输入则从刚才预测系统更新的值取。然后本地再次转为定点数执行逻辑帧，最后再进行更新，并更新错误的缓冲区快照。

**🦉评判：** ⚠️ **需要纠正**。整体方向说对了（队列+字典→快照恢复→重放），但有**3个细节错误**：

1. ❌ **"更新最后记录指针"** — 没有这个操作。`_lastRemoteInput` 在收到真实数据时无条件更新（`PredictRemote` 第 82 行），跟验证结果无关，不存在"验证通过才更新"的逻辑。
2. ❌ **"如果控制器没有传入真实值，那就以上一次输入来进行预测"** — 这不是"初始5帧的特例"，而是**每帧**都是这样。`else` 分支（无数据时）永远返回 `_lastRemoteInput`，不管是多少帧。
3. ⚠️ **关键假设没说透**：验证时用的真实数据是"当前收到的"，但验证的对象是"队列里最早的旧预测帧"——两者不是同一帧。**整个设计最核心的假设是"FIFO 顺序匹配"**：第 N 个数据包 = 第 N 个预测帧。帅老大提到了这个链路但没有点明这是"假设"。

**💜小爱参考回答（面试标准—修正版）：**
**总结：DoRollback 的核心是三步——发现错误、回到安全位置、用正确输入重跑覆盖。** 展开来说：第一阶段"发现错误"——当真实网络数据从 FIFO 队列到达时，PredictRemote 从 `_predictedFrameQueue` 弹出一个最早记录的预测帧号（假设帧 N），用这个帧号去 `_predictionHistory` 查当时的预测值，对应当前收到的真实数据做对比。注意这里的核心假设是"FIFO 顺序匹配"——第 K 个数据包对应第 K 个被预测的帧，延迟越大队列越长，验证的预测帧就越"老"。如果不同，设置 `_pendingErrorFrame = N` 和 `_correctRemoteRaw = 真实数据`。第二阶段"退回安全位置"——OnFrameUpdate 末尾检测到回滚时，调用`RestoreSnapshot(errorFrame - 1)`。这里减 1 的原因是 `errorFrame` 的快照基于错误预测产生，恢复它没有意义，必须回到错误发生前的状态。第三阶段"重放纠正"——从 FrameBuffer 取本地真实 Input，用 `_correctRemoteRaw` 构造正确远程 Input，执行一次位置计算，覆盖 errorFrame 的旧快照。

---

#### 子问题②：为什么 safeFrame = errorFrame - 1

**问题：** 为什么用 `safeFrame = errorFrame - 1`（退到前一帧）而不是 `errorFrame` 本身？`errorFrame` 不正是出问题的那一帧吗，为什么不能直接回到它？

**帅老大回答：**
因为 errorFrame 是发生错误的帧，如果直接使用这个错误帧，就相当于使用错误帧来执行其他玩家的输入，这样会导致运行结果状态不正确。

**🦉评判：** ✅ **方向正确，但只说了一半**。关键点说对了——"errorFrame 的状态是错的"这个直觉完全正确。但没说出来更深层的**原因**：errorFrame 的快照 S_N 本身就是基于错误预测值产生的（没有真实数据→用预测值执行→拍快照 S_N），所以恢复 S_N 相当于"用一个错的状态去修正另一个错"，必然不正确。正确做法是回到 errorFrame - 1（错误还没发生时，S_{N-1} 是安全的），用正确的远程 Input 重跑 errorFrame。

**💜小爱参考回答（面试标准—修正版）：**
**总结：errorFrame 的快照基于错误预测产生，恢复它等于恢复了一个错误状态；所以必须退到 errorFrame - 1（错误发生前的安全帧），用正确 Input 重新执行才能得到正确答案。** 展开来说：`errorFrame` 这一帧在回滚前的执行过程是——帧 N 的真实数据没到，用预测值执行了逻辑帧，然后拍了快照 S_N。**S_N 基于错误预测**，如果 `RestoreSnapshot(errorFrame)` 恢复的是 S_N，那等于"用一个错的状态去修正另一个错"，毫无意义。正确做法是 `RestoreSnapshot(errorFrame - 1)`——帧 N-1 执行时用的是安全的数据，S_{N-1} 是正确的，退回去后用正确的远程 Input（`_correctRemoteRaw`）重新执行帧 N，最后覆盖 S_N。这个减 1 的本质是"用历史安全点重放，而不是在错误点上修改"。类比：**文档写错了某段，你一定回到上一个正确的版本重新写这一段，而不是在错误的版本上改来改去——那只会越改越乱。**

### Q15：MarkRead 在阶段四的含义

**问题：** `_frameBuffer.MarkRead(frameID - 4)` 在阶段三的意义是"延迟4帧视觉效果"。在阶段四加入了预测+回滚之后，MarkRead 的含义有没有变化？还是说应该移动 MarkRead 的位置——比如移到服务器确认后？为什么？

**帅老大回答：**
MarkRead 是标记帧已经消费。在阶段三没有加入网络的情况下，主要是模拟网络延迟，让缓冲区有模拟的帧刷新。加入网络过后，主要目的是在触发追帧的时候，`_frameBuffer.MarkRead(frameID - 4)` 标记往前推4帧，表示当前帧的前4帧都是待消费的状态，主要是方便缓冲区面板的更新，实际上对于帧同步来说没有太多实际意义。

**🦉评判：** ❌ **有大问题。** 帅老大说"MarkRead 加入网络后没有太多实际意义"——这会严重不对。**联网后 MarkRead 是整个回滚安全机制的锚点。** 让我给你讲透。

阶段三（无预测+回滚）：MarkRead 确实只是视觉效果，`frameID - 4` 让 Buffer 面板上有黄色"待消费"区域。

阶段四（有预测+回滚）：**MarkRead 标记的位置 = "永远不会被回滚的最新帧号"**。只有 <= MarkRead 的帧才是已经被服务器确认的、绝对不会被回滚的安全帧。**所以 MarkRead 必须等服务器确认后才能推进**，而不是每帧自动推进。

```
正确做法（阶段四）：
  收到服务器确认帧 N → MarkRead(N)
  只有已确认的帧才能 MarkRead
  未确认的帧必须保留（可能被回滚）

当前代码的问题：
  ExecuteOneFrame 每帧都 MarkRead(frameID - 4)
  → 这和服务器确认完全解耦！
  → 如果帧102的数据错了要回滚到帧100
    但 MarkRead 已经推进到了帧103
    那帧100的快照已经被覆盖了 → 回滚不了！
```

这里其实是**阶段四代码里的一个设计缺陷**——`FrameEngine.ExecuteOneFrame()` 第 129 行的 `MarkRead(frameID - 4)` 在阶段四模式下应该被抑制，由服务器确认信号来控制。目前代码里 `MarkRead` 依然每帧自动推进，这和预测+回滚机制是矛盾的。**这是一个遗留的 P0 级设计问题。**

**💜小爱参考回答（面试标准）：**
**总结：MarkRead 在阶段三只是视觉缓冲，在阶段四则是"安全确认边界"——告诉系统"这些帧永远不会被回滚了"。MarkRead 必须由服务器确认驱动，而不是每帧自动推进。** 展开来说：阶段四加入预测+回滚后，帧分成了两个区域——"已确认区域"（<= MarkRead，永不被回滚）和"未确认区域"（> MarkRead，可能被回滚）。如果 MarkRead 还在每帧自动推进（`frameID - 4`），就破坏了这层语义——还没等到服务器确认，MarkRead 就把那些帧标记为已消费，对应的快照也被覆盖了，回滚时就没有可恢复的数据了。正确的做法是：MarkRead 只在收到服务器确认时推进（`MarkRead(confirmedFrame)`），FrameEngine 里那个自动 `MarkRead(frameID - 4)` 在联网模式下必须去掉。**这个减 4 从"模拟网络延迟"变成了"等待服务器确认的缓冲窗口"，语义完全变了。**
