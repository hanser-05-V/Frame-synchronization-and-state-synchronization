## 阶段一：吃透单机代码

---

### Q1：单机项目不联网，为什么不直接用 float？

**帅老大回答：**
float 会有精度问题，根据不同设备的性能会有差异，这样就不能保证用户输入的准确性，得到的结果会有偏差。

**评价：** ✅ 通过

**补充：**
同一个 CPU、同一个 exe、同一次运行中，float 运算其实是确定的。帧同步用定点数的真正原因是**跨场景**的不确定性——IL2CPP vs Mono、x86 vs ARM、Debug vs Release——这些会导致 float 结果不同。定点数解决的是"录制的回放在任何机器上都能复现"。

---

### Q2：录制了 100 帧 Input，回放时只喂 Input 不记录碰撞。方块在第 50 帧撞墙怎么办？

**帅老大回答：**
因为记录了录制时候的开始帧位置，以及这段时间的输入，他必定是以同样的状态发生碰撞，所以也不需要记录碰撞。

**评价：** ✅ 满分

**补充：**
只存"因"（Input + 起点），不存"果"（碰撞 / 轨迹）。"果"由"因"通过确定性逻辑自然计算出来。

---

### Q3：Demo 里 FrameBuffer 每写一帧立刻 MarkRead。主程说"这跟直接调 Update 没区别"——说得对不对？

**帅老大回答：**
目前单机测试下缓冲区确实几乎没有延迟就下发命令了。但是后续接入网络后便会体现出作用——客户端发送输入指令进入待缓冲区，服务器接受下发命令到缓冲区，最后客户端按照一定步长来进行处理。目前运动逻辑层和渲染层还没有分开，只是在 Update 加入了帧判断机制用于追帧。后续加入网络或功能复杂起来，分离逻辑层和渲染层分开执行，这也是帧同步和一般 Update 之间的区别。

**评价：** ✅ 正确。

**补充：**
联网后服务器的具体作用——不只是转发，权威服务器还需要对输入进行校验防止作弊，玩家挂机时服务器会做出相应措施。P2P 帧同步存在但当前主流的还是客户端+服务器模式。

---

### Q4：OnRequestInput 为什么存在

**帅老大回答：**
通过 `Func<FrameInput[]>` 委托，引擎每帧拉取输入。FrameEngine 只管"给我 Input[]"，不关心来源。ReadInput 返回 FrameInput 数组传递。单机时指向键盘，联网时可换指向网络——不改引擎代码。

**评价：** ✅ 理解了委托替换机制。

---

### Q5：录制回放链路

**帅老大回答：**
recordedFrameCount 在 Debugger 中增加，Controller 执行完一帧同步调用 Debugger 更新。按 R 开始记录，初始为 0。playbackFrame 递增，当超过记录的帧数则回放结束。

**评价：** ✅

**补充：**
两个计数器都在 `FrameDebugger.UpdateFrame()` 中递增，被 `GameController.ReadInputs()` 和 `OnFrameUpdate()` 读取来判断回放结束。

---

### Q6：追帧机制深入

**帅老大回答：**
采用 for 循环一轮跑完就不跑了，当有玩家有网络延迟便会漏掉信息不能同步。追帧瞬间移动是帧同步的设计就是这样的，当一方客户端卡顿恢复后，会进行追帧，执行帧操作，一直到追上目前的帧为止。

**评价：** ✅ 正确。用 for 确实会漏帧；瞬移是设计如此，不是 Bug。

---

### Q7：定点数精度/溢出

**帅老大回答：**
Scale=1000 用于去除小数影响，保留 3 位小数。相乘使用同余原理除以 Scale。

**评价：** ✅ 思路对，需注意溢出细节。

**补充：**
- `a._raw * b._raw` 在 int 空间可能溢出（50000×50000=2,500,000,000 > int.MaxValue）
- 正确写法应用 `long` 中间值：`(int)((long)a._raw * b._raw / SCALE)`
- "同余原理"不适用——这里不是取模，是两个 ×1000 的数相乘 = ×1,000,000，除 1000 恢复 ×1000 标度

## 阶段二：面试级理解

---

### Q8：环形缓冲深挖 — 256够用吗？帧号溢出？600帧追帧？

**帅老大回答：**
256容量一次性推600帧过来，会在while循环中不断检测然后按帧执行追帧。连续性检测可以通过，只要不是跳跃执行帧就不会出问题。

**评价：** ⚠ 80分

**补充：**
追帧时**生产=消费=1帧**，每一帧是先写入→立即执行→立即MarkRead，被覆盖的槽位都是已消费完的旧帧。256够不是因为数字大，而是因为边写边消费。

如果600帧先全部写入再执行，后面的帧会覆盖还没消费的前面帧——那才会出问题。

关于帧号溢出：`_currentFrame` 用 `int` 存储，int.MaxValue ≈ 1,970 年的帧数据。真正的帧同步游戏每局比赛开始帧号归零。`MarkRead` 用 `if (frameID > _lastReadFrame)` 防住了负帧号。

---

### Q9：MarkRead延迟4帧 — 改成0会怎样？（联网方向评判）

**帅老大回答（联网方向）：**
改成0游戏逻辑还是能正常运行，只是发生卡顿过后，会导致没有缓冲带，信息会丢失掉，导致客户端之间会出现不同步现象。

**评价：** ✅ 85分 — 联网方向正确

**补充：**
联网后 MarkRead 的真正含义——帧写入→本地预测执行→等待服务器确认。服务器回包确认后 MarkRead，这些帧才安全。未确认的帧不能被 MarkRead，可能被回滚。

帅老大的直觉完全对——"没有缓冲带"="没有等待确认的窗口期"；"信息丢失"="未确认帧被标记为已消费后无法回滚"；"不同步"="没有可退的快照"。

## 阶段三：网络帧同步

---

### Q10：分配机制

**问题：** 客户端 1 先连服务器，客户端 2 后连。为什么客户端 1 只能控制自己的 P1，客户端 2 只能控制自己的 P2？

**帅老大回答：**
在读取输入时候，根据加入服务器的前后，目前是根据这个得到 playerIndex。后续读取输入时候，会根据 playerIndex 来采用不同的读取输入方式，这样来区别输入，另外一个的输入从网络端进行读取。后续都是 exe 时候还需要实际区分出 ID。

**评价：** ✅ 通过

**补充：**
```
客户端1 (playerIndex=0):
  inputs[0] = ReadP1Input()     ← 自己读键盘
  inputs[1] = 从网络队列取       ← 对方Input

客户端2 (playerIndex=1):
  inputs[0] = 从网络队列取       ← 对方Input
  inputs[1] = ReadP2Input()     ← 自己读键盘
```
两个客户端的 FrameInput[2] 完全相同 → 帧同步成立。FrameEngine 不关心 Input 来自键盘还是网络。

---

### Q11：TCP vs UDP

**问题：** 帧同步最终目标是跑 UDP，为什么先跑 TCP？

**帅老大回答：**
TCP 相较于 UDP 来说链接更加稳定，步骤也相对简单，每一步都有确切的监听。UDP 是面向无连接的，直接发送消息，延迟低但是不稳定。在强调及时性对抗的游戏，UDP 使用比 TCP 更高。现在还在项目初期，先使用稳定的 TCP 测试功能，后续更进优化为 KCP，结合了 TCP 和 UDP，在消耗一定带宽的前提下，提高 TCP 的连接速度，防止出现和刚才一样延迟导致的不同步情况。

**评价：** ✅ 通过

**补充：**
TCP 有队头阻塞——丢一包后面都得等。帧同步中，这导致 Input 队列被打断，30FPS 的节奏乱掉。UDP 丢了不管，少一帧用上一帧推算就行，帧同步宁可丢帧也不接受延迟波动。

KCP 是基于 UDP 的可靠传输协议，在牺牲一定带宽（多发一些 ACK）的前提下，比 TCP 快 10-30%。它保留了 UDP 的无阻塞特性，同时自己实现重传保证最终一致性。帅老大提到了 KCP，说明对"生产级帧同步用什么传输层"有清晰的认知。
