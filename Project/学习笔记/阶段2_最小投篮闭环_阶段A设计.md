### 投篮流程 — Q1：按下投篮键后，同一逻辑帧应如何完成出手？

**问题：**

P0初始满足：

```text
P0.hasBall = true
P0.state = Idle
ball.holderPlayerIndex = 0
ball.state = Held
```

这一逻辑帧收到 `FrameInput.shoot=true` 后，在 `BallPhysicsSystem` 开始计算前，玩家状态、球权、出手位置和速度应该按照什么顺序变化？同时说明无球投篮如何处理。

**帅老大首次回答原文：**

> 当投篮时候，玩家进入 shootReady 举球待投 ，  确认投篮过后 进入到投篮状态， 对应的 球变成 空中状态， 球权力 P0 hasBall变成false , 球对应 hoderPlayerIndex  有变成-1 （表示不然持球），状态变为空中

**输入方案选择原文：**

> 先按照 按下就出手处理， 后面丰富再加 改成 按住然后松手后再进行出手

**帅老大第一次修正原文：**

> 具体流程是 按下投篮键 ，检查持球状态，没有球就拒绝状态切换请求，如果有球 就进入shoot状态， 并设置好球的初始速度，运动方向， 同时接触球权 ，球现在进入到空中状态

**帅老大最终回答原文：**

> 检查有没有球 ， 失败则保持当前 状态 ， 有球就进入到ShootReady ，然后再 Shooting ，把ball.position 设置为当前出手的位置， 设置好初速度和运动方向， player.hasBall=false ,  ball.holderPlayerIndex=-1 , ball.state= 空中状态，OnPostFrameUpdate 调用 球物理系统   BallPhysicsSystem.Update

**评价：** ✅ 通过，出手位置和速度公式留到后续问题确定

**已拍板设计：**

首版使用“按下即出手”：

```text
shoot从false变为true
→ 同一逻辑帧完成ShootReady
→ 同一逻辑帧进入Shooting
→ 释放球并进入Airborne
```

`ShootReady` 在首版只是同帧过渡状态，不要求画面停留。后续丰富玩法时，再改为“按住进入 ShootReady，松开后进入 Shooting”。

**❌ 错误点：**

1. **首次流程缺少无球分支。** 玩家无球时必须拒绝投篮，玩家状态和球状态都保持不变。
2. **首次流程缺少球的初速度。** 只把球切换到 Airborne 而不设置速度，会导致球原地或只受重力下落。
3. **“进入shoot状态”不精确。** 当前枚举没有笼统的 Shoot 状态，必须明确经过 `ShootReady → Shooting`。
4. **“解除球权”必须落到具体字段。** `player.hasBall=false` 与 `ball.holderPlayerIndex=-1` 必须同步修改。
5. **出手位置仍是抽象描述。** “当前出手位置”的确定性计算方式需要在下一题明确。

**✅ 正确点：**

1. 正确使用 `hasBall` 作为投篮前置条件。
2. 无球时选择拒绝转换并保持当前状态。
3. 正确描述同一逻辑帧内 `ShootReady → Shooting` 的状态转换。
4. 知道球进入物理系统前必须设置出手位置、初速度和运动方向。
5. 能同步解除玩家和球两侧的持球关系。
6. 正确把 `BallPhysicsSystem.Update` 放在 `OnPostFrameUpdate` 阶段执行。

**💜 参考回答（面试标准）：**

首版采用按下即出手。收到 `shoot=true` 后，先校验玩家确实持球，并验证球状态为 Held、持有者索引等于该玩家；任一条件失败就拒绝投篮，所有状态保持不变。校验通过后，状态机在同一逻辑帧依次执行 `ShootReady → Shooting`，随后设置确定性的出手位置和初速度，再同步写入 `player.hasBall=false`、`ball.holderPlayerIndex=-1`，最后把球切换为 Airborne。`OnPostFrameUpdate` 看到 Airborne 后调用 `BallPhysicsSystem.Update` 推进轨迹。这样物理系统不会观察到“玩家已无球但球仍为Held”的中间状态。

### 投篮轨迹 — Q3：自动瞄准使用哪种方式生成抛物线？

**问题：**

自动瞄准确定后，首版选择哪一种轨迹生成方式？为什么它更适合当前的帧同步演示？

- A：固定飞行帧数，规定球经过 N 个逻辑帧到达篮筐，再反算初速度。
- B：固定出手速度和角度，玩家距离改变后允许投丢。
- C：针对不同投篮点配置预设初速度。

**帅老大回答原文：**

> A

**评价：** ✅ 通过，选择与“确定性、稳定命中、快速形成演示”的目标一致

**已拍板设计：**

首版使用固定飞行帧数方案。投篮开始时确定固定的飞行帧数 N，根据逻辑层的固定点出手位置、固定篮筐目标位置、固定逻辑帧间隔和重力，反算球的初速度。轨迹运算只读取同步状态，不读取渲染层或墙钟时间。

**❌ 错误点：**

无。本题的方案选择正确；尚未展开选择理由和计算流程，这部分将在下一题继续验证。

**✅ 正确点：**

2. 相同输入和同步状态能够得到相同初速度，符合帧同步确定性要求。
3. 相比固定速度和角度，它更容易适配不同出手位置。
4. 相比逐点配置轨迹，它减少了首版配置量并保留了扩展能力。

**💜 参考回答（面试标准）：**

首版选择A，规定篮球经过固定的 N 个逻辑帧到达篮筐，再根据出手点、目标点、固定帧间隔和重力反算初速度。它把“何时到达”变成明确约束，能适配不同出手位置，也便于制作稳定命中的演示。所有参与计算的数据都来自同步逻辑层，并使用固定点数；相同帧状态必然得到相同轨迹。与固定角度、速度相比，它更容易保证命中；与预设轨迹表相比，它减少配置量，后续也能自然扩展距离和力度变化。

### 投篮轨迹 — Q4：如何计算确定性出手位置和初速度？

**问题：**

已知逻辑层出手位置 `S`、篮筐目标位置 `T`、固定飞行帧数 `N`、固定帧间隔 `dt` 和重力 `g`，请用自然语言与伪代码说明：如何确定 `S`，如何计算 X、Y、Z 三个初速度分量，使球按当前“先更新速度、再更新位置”的离散物理顺序，在第 N 帧到达 `T`；同时说明为什么不能读取 `Transform.position`。

**帅老大首次回答原文：**

> 出手位置 就 根据玩家逻辑位置 然后加上  竖直方向玩家的 身高和手臂上 ，速度分量是 先根据 距离篮板距离，然后和固定帧长算出 速度，然后对应分到xyz, Transform.position 这里得使用确定的数据 避免flaot 误差

**帅老大表示卡住原文：**

> 这里不清楚

**XZ拆题回答原文：**

> 3，2

**两帧Y轴拆题回答原文：**

> 2

**帅老大推导通式原文：**

> float deltaY = T.y - S.y;
> float v0 = deltaY / (N * dt) - 0.5f * g * dt * (N + 1);

**帅老大首次固定点修正原文：**

> FixedInt deltaY =  new FixedInt (T.y - S.y);
> FixedInt v0 = deltaY / (N * dt) - 0.5f * g * dt * (N + 1

**帅老大首次确定性解释原文：**

> 0.5f 为 浮点数，会给结果带来小数，会造成精度差问题 ，要保整输入一致，所以才使用  FixedInt.Half

**帅老大最终复述原文：**

> 0.5f 属于浮点数。一方面不能直接和 FixedInt 运算，即使转化计算过后， 会因为平台和设备的不同 来导致结果差异， 而 FixedInt.Half 内部定义的 就是 FixedInt 的一半，数值固定 为缩放倍数的 一半， 用确定是数值参与，可以确保各个客户端的运算和回滚结果一致

**评价：** ⚠️ 通过，但需要重练习。数学公式最终正确，确定性原因也已修正；过程依赖多次拆题和参考写法，后续应进行一次无提示复述。

**已拍板设计：**

```text
S = 玩家逻辑位置 + 固定向上偏移 + 固定出手方向偏移
T = 篮筐的固定点逻辑命中位置
frameCount = FixedInt.FromInt(N)
totalTime = frameCount × dt
delta = T - S

velocity.x = delta.x ÷ totalTime
velocity.z = delta.z ÷ totalTime
velocity.y = delta.y ÷ totalTime
             - FixedInt.Half × g × dt × FixedInt.FromInt(N + 1)

ball.position = S
ball.velocity = FixedVector3(velocity.x, velocity.y, velocity.z)
```

该 Y 轴公式专门匹配当前半隐式欧拉顺序：每帧先执行 `velocity.y += g × dt`，再执行 `position += velocity × dt`。

**❌ 错误点：**

1. 首次回答把目标描述为“篮板”，首版自动瞄准的目标应是篮筐逻辑命中点。
2. 首次出手点只提到高度，遗漏固定前向或出手方向偏移，可能导致球从角色身体中心飞出。
3. “先算总速度再分到XYZ”不准确；应先求 `T-S`，再分别计算 XZ 匀速分量和带重力补偿的 Y 分量。
4. 首次没有考虑重力以及当前“先改速度、后改位置”的离散更新顺序。
5. 对 `Transform.position` 的风险解释不完整：它不仅使用浮点，还属于表现层，可能经过插值，回滚后也不一定是权威逻辑位置。
6. 通式虽然推导正确，但使用了 `float` 和 `0.5f`，违反同步逻辑只使用固定点数据的约束。
7. `new FixedInt(T.y-S.y)` 的思路错误：`T.y-S.y` 已经是 `FixedInt`；同时构造函数接收的是内部原始值，不等价于 `FromInt`。
8. “浮点会带来小数”不是核心原因；固定点同样表示小数，核心是跨平台运算结果的确定性。

**✅ 正确点：**

1. 从玩家逻辑位置和固定手部高度计算出手点，方向正确。
2. 能用 `N × dt` 得到固定总飞行时间。
3. 正确算出 XZ 匀速分量，理解 `速度=位移÷时间`。
4. 能通过两帧展开理解重力逐帧累计，并正确求出示例中的初始 Y 速度。
5. 正确推导出适配半隐式欧拉顺序的 Y 轴初速度公式。
6. 最终能区分浮点体系和固定点体系，并说明跨平台与回滚重演一致性的要求。
7. 正确理解 `FixedInt.Half` 使用固定缩放值表示二分之一。

**💜 参考回答（面试标准）：**

出手点必须来自同步逻辑状态：以玩家的 `FixedVector3` 坐标为基准，叠加固定的手部高度和出手方向偏移，不能读取可能经过插值的 `Transform`。设位移为 `T-S`，总时间为 `N×dt`，则 XZ 初速度分别是对应位移除以总时间。由于物理系统每帧先加重力再更新位置，N 帧累计重力位移为 `g×dt²×N×(N+1)/2`，所以 Y 初速度为 `deltaY/(N×dt)-Half×g×dt×(N+1)`。全部使用 `FixedInt`，确保客户端预测和回滚重演一致。

### 持球表现 — Q5：Held 状态下如何让球确定性地跟随玩家？

**问题：**

玩家移动完成后，球处于 `Held` 状态。请设计持球跟随流程：由哪个逻辑系统负责、何时执行、校验哪些球权字段、怎样计算固定手部挂点、修改 `BallEntity` 的哪些字段，以及何时把逻辑坐标同步给 `Transform`。

**帅老大首次回答原文：**

> 球应该是根据玩家前进方向  在玩家前面一点固定位置 落下， 然后弹起到另外一只手，这里具体 应该是 有 球的物理系统 管理球的移动 ， 对于运动来说 ，起点和终点 都是知道的 ， 进行计算就好，  具体在玩家持球就开始执行， 最终 只需要校验 球的状态 state , holderPlayerIndex , velocity ，最终修改这些

**帅老大第二次回答原文：**

> 检查球的位置 和 速度  ， 可以在玩家具体 手部位置添加空物体，然后 引用到BallPossessionSystem ， 具体修改BallEntity 的 state状态， 最后在 球物理帧更新 时候 给球 的 Transform 上

**帅老大流程复述原文：**

> 具体流程是 在玩家移动完成过后 ，球管系统 负责更新玩家球权标记，以及 更新球的状态为 held ,当 球员状态不对， 可能是因为被抢断等， 变不在更新球的一致，  在球权和玩家都对的情况下， 再更新球的位置， 和位置， 保存快照， 最后再渲染层 更新转换 成 transform 来更新 球位置

**帅老大最终回答原文：**

> 检验 球权（ 玩家是否有球 hasBall ， 球的状态 ，球hoderPlayerIndex ）， 后面修改球的位置  和 速度

**评价：** ⚠️ 通过，但需要重练习。最终能区分“球权校验字段”和“跟随修改字段”，但过程多次混淆运球、物理、Transform 与球权事务的职责。

**已拍板设计：**

```text
玩家逻辑移动完成
→ BallPossessionSystem.UpdateHeldBall(player, ball)
→ 校验 player.hasBall == true
→ 校验 ball.state == Held
→ 校验 ball.holderPlayerIndex == player.playerIndex
→ 任一失败：不更新位置，并报告球权不一致
→ 全部通过：
   handPosition = player.position
                  + 固定向上偏移
                  + player.facing × 固定前向偏移
   ball.position = handPosition
   ball.velocity = FixedVector3.Zero
→ ball.state 与 holderPlayerIndex 保持不变
→ 保存包含玩家和球的完整逻辑快照
→ 表现更新阶段再将 ball.position 转换后写入 Transform
```

首版不实现落地反弹、左右手切换和运球周期；这些属于后续运球系统扩展。

**❌ 错误点：**

1. 首次回答设计成运球反弹，超出当前“Held 固定挂点”的最小演示范围。
2. 把 Held 跟随交给 `BallPhysicsSystem`，混淆了球权附着与 Airborne/Free 物理职责。
3. 校验字段不完整，遗漏 `player.hasBall` 以及持有者索引与玩家索引的一致性比较。
4. 提议读取手部空物体，等于让确定性逻辑依赖 `Transform` 浮点表现数据。
5. 跟随阶段不应该每帧强制修改 `hasBall`、`state` 或 `holderPlayerIndex`，否则会掩盖球权不一致。
6. 正常跟随需要修改 `ball.position` 并把 `ball.velocity` 置零，而不是修改球权状态。
7. `Transform` 更新属于表现同步，必须发生在逻辑状态更新和快照保存之后，不能作为逻辑输入。

**✅ 正确点：**

1. 知道球的行为应由系统负责，而不是塞进 `BallEntity` 数据实体。
2. 注意到了 `state`、`holderPlayerIndex` 和速度等关键字段。
3. 能识别逻辑状态应该先保存快照，再更新表现层 `Transform`。
4. 最终准确说出三项校验：`player.hasBall`、`ball.state`、`ball.holderPlayerIndex`。
5. 最终准确说出 Held 跟随只修改球的位置和速度。

**💜 参考回答（面试标准）：**

玩家逻辑移动完成后，由 `BallPossessionSystem` 处理 Held 跟随。系统先校验玩家 `hasBall=true`、球状态为 Held，并且 `holderPlayerIndex` 等于该玩家索引；失败时不静默修复球权，而是停止跟随并报告不变量错误。校验通过后，用玩家的固定点逻辑坐标、朝向、固定高度和前向偏移算出手部挂点，只写入 `ball.position` 并将 `ball.velocity` 清零，球权字段保持不变。随后保存完整快照，最后由表现层把逻辑坐标转换到 `Transform`。运球反弹另设系统，首版不实现。
