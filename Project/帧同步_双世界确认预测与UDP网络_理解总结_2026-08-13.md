# 帧同步双世界、表现缓冲与 UDP 网络理解总结

> 日期：2026-08-13  
> 范围：Route C 当前表现延迟方案、街篮2式 Confirmed/Predicted 双世界、回滚与追帧、TCP/UDP/KCP、丢包与重连。  
> 说明：本文记录当前学习讨论形成的准确模型。目标架构不等于 Route C 已全部实现；当前 P2-A 已建立统一确定性世界基础，InputLedger、双世界和 ViewWorldBuilder 仍属于后续 P2-B～P2-D。

---

## 一、最重要的结论

1. Route C 当前的远端表现延迟，是**延迟播放预测世界中的旧帧**；街篮2式方案是让远端优先播放**确认世界中的安全帧**。
2. 固定延迟只能按“帧有多旧”猜测它是否安全；`ConfirmedFrame` 根据“双方 Actual 输入是否连续完整”证明它是否安全。
3. 本地输入虽然是 Actual，但远端输入可能仍是 Predicted；因为球权、碰撞、拾球等结果依赖双方，所以整帧世界仍属于 Predicted World。
4. `Actual == Predicted` 只决定是否需要纠正预测世界，不决定该帧能否确认。能否确认只取决于双方 Actual 是否完整且不存在前序空洞。
5. 双世界不能消灭网络问题。它将“先猜着走、猜错后回抽”替换为“只按事实展示、事实长期不到时可能停顿”。
6. 回滚重演、逻辑追帧、表现追赶是三件不同的事，不能混用“追帧”这个词。
7. UDP 不应理解为放弃可靠性，而是让游戏按业务需要自行决定可靠、顺序、重传和过期策略。

## 二、Route C 表现延迟与双世界的区别

### 2.1 Route C 当前方案

当前 P1-G 表现端点大致为：

```text
本地玩家：N-1 → N
远端玩家：N-3 → N-2
```

远端相对本地多落后约两个逻辑帧。它的作用是给远端真实输入更多到达时间，从概率上减少已经显示的帧被回滚改写。

但 `N-3`、`N-2` 仍可能来自 Predicted World：

```text
PredictedFrame = 100
ConfirmedFrame = 96
远端显示      = 97 → 98
```

这里 97、98 尚未确认。如果之后 Actual 与预测不同，历史会被重演，已显示的位置仍可能回抽。

因此：

```text
Route C 固定延迟 = 晚一点展示猜测
```

### 2.2 双世界方案

双世界维护两条独立状态轨道：

```text
Confirmed World：只消费双方连续完整的 Actual
Predicted World：消费 Actual，以及缺失部分的 Predicted
```

表现来源通常是：

```text
本地玩家 ← Predicted World
远端玩家 ← Confirmed World 历史
篮球     ← 根据持球、传球、投篮语义在两者之间仲裁
```

同一时刻可能是：

```text
PredictedFrame     = 100
ConfirmedFrame     = 96
RemoteDisplayFrame = 94.4
```

含义：

- 本地逻辑已低延迟运行到 100；
- 双方 Actual 连续完整到 96；
- 远端画面正在确认快照 94→95 之间插值；
- 远端仍有约 1.6 帧确认库存可播放。

因此：

```text
双世界远端表现 = 晚一点展示已经成立的事实
```

## 三、三个帧头与两个重要差值

### 3.1 三个游标

#### PredictedFrame

预测世界已经执行到的逻辑帧。它通常最靠前，为本地玩家提供低延迟响应。

#### ConfirmedFrame

确认世界已经使用双方 Actual 真正执行到的帧。它不是“本地玩家实际逻辑帧”，也不是服务器权威帧。

#### RemoteDisplayFrame

远端表现当前播放到的确认时间线位置，可以是小数，例如 94.4 表示正在 94→95 插值。

正常关系：

```text
RemoteDisplayFrame <= ConfirmedFrame <= PredictedFrame
```

### 3.2 两个差值

```text
PredictionLead = PredictedFrame - ConfirmedFrame
```

表示有多少逻辑帧仍处于预测区。

```text
ConfirmedInventory = ConfirmedFrame - RemoteDisplayFrame
```

表示远端表现还有多少安全库存可播放。

差值不是第三套世界，而是由帧头计算出的诊断量。

## 四、确认条件与预测验证

必须牢牢记住：

```text
双方 Actual 是否连续完整
→ 决定 ConfirmedFrame 能否推进

Actual 是否等于当时使用的 Predicted
→ 决定 Predicted World 是否需要重建
```

例如当前 `ConfirmedFrame=96`：

| 第 97 帧情况 | ConfirmedFrame | Predicted World |
|---|---:|---|
| Actual 到达且预测命中 | 推进到 97 | 无需重建 |
| Actual 到达但预测失败 | 仍可推进到 97 | 需要纠正或重建 |
| Actual 未到达 | 停在 96 | 97 仍属于预测区 |

如果 98 Actual 先到、97 缢失：

```text
InputLedger[98] = Actual
InputLedger[97] = Missing
ConfirmedFrame  = 96
```

确认世界不能越过空洞，因为状态具有顺序依赖：

```text
State98 = Step(State97, Input98)
State97 = Step(State96, Input97)
```

## 五、双世界轨道、容器和事件

### 5.1 双世界不是简单的两个数组

更准确的结构是一个轨道类型的两个实例：

```text
FrameSyncCoordinator
├─ InputLedger
├─ ConfirmedTrack
│  ├─ ConfirmedFrame
│  ├─ DeterministicWorld
│  ├─ SnapshotBuffer
│  └─ ConfirmedEventJournal
├─ PredictedTrack
│  ├─ PredictedFrame
│  ├─ DeterministicWorld
│  ├─ SnapshotBuffer
│  └─ PredictedEventJournal
└─ ViewWorldBuilder
```

两条轨道拥有独立状态实例、帧头、快照和事件提交状态，但共享：

- 同一个 InputLedger；
- 同一套确定性 `Step`；
- 同一个初始世界；
- 同一种事件 ID 规则；
- `ConfirmedFrame <= PredictedFrame` 等不变量。

它们不是“本质没有关系”，而是**状态实例独立、输入事实和模拟契约共享**。

### 5.2 InputLedger 不等于 Dictionary

`InputLedger` 是职责，不是固定容器类型。每帧可以记录：

```text
FrameInputRecord
├─ LocalActual
├─ RemoteActual?
├─ RemotePredictedUsed?
└─ Missing / Predicted / Confirmed / Mismatch
```

实现可以使用：

- `Dictionary<int, FrameInputRecord>`：适合原型、测试和乱序写入；
- 环形缓冲：固定内存，适合长期实时战斗；
- 帧号索引数组：适合明确窗口范围的实现。

环形缓冲槽位必须保存完整 `frameID`，防止取到被模运算覆盖的旧数据。

### 5.3 三类容器不能混淆

```text
NetworkReceiveQueue
→ 暂存刚到达的网络包，按到达顺序排空

InputLedger[frameID]
→ 按逻辑帧保存输入事实、预测值和验证状态

SnapshotBuffer[frameID]
→ 保存执行完该帧后的世界状态
```

网络队列描述到达顺序；InputLedger 描述逻辑帧顺序；SnapshotBuffer 描述世界恢复点。

### 5.4 稳定事件 ID

确定性模拟可以产生领域事件，但不能直接播放音效和特效。

```text
EventID = CanonicalFrame + EntityID + EventType + FrameLocalSequence
```

例如：

```text
98 / Player0 / ShootReleased / 0
```

回滚重演后会重新生成同一 ID，表现层可据此去重或将预测事件升级为确认事件。

原则：

```text
影响未来逻辑的事实 → SimulationWorldState
仅通知表现的瞬时信息 → EventJournal
动画、音效、粒子副作用 → PresentationEventDispatcher
```

## 六、回滚重演、逻辑追帧与表现追赶

### 6.1 回滚重演

目的：纠正已经执行过的错误历史。

```text
恢复错误帧之前的快照
→ 用 Actual 和重新生成的 Predicted 重演
→ 回到原 PredictedFrame
```

回滚是每个客户端根据自己的预测历史独立触发的，不要求双端同时回滚。双方的回滚次数、时机和重演长度可以不同。

### 6.2 逻辑追帧

目的：追上墙钟调度目标。

```text
回滚重演结束：PredictedFrame = 100
当前调度目标：TargetLogicFrame = 103
→ 再执行 101、102、103
```

回滚不一定导致逻辑追帧；只有运算耗时使逻辑调度落后时才需要。

### 6.3 表现追赶

目的：让远端播放库存恢复到目标深度。

```text
ConfirmedFrame = 103
RemoteDisplayFrame = 98
ConfirmedInventory = 5
```

表现层可以短时间以 1.05～1.15 倍速度顺序播放 98→99→100……，而不是直接从 98 插值到 103。

### 6.4 三者的关系

逻辑追帧不能直接修改表现指针，表现层也不能控制逻辑 `Step`。但存在间接数据关系：

```text
逻辑轨道快速执行
→ 产生更多世界快照并推进帧头
→ 改变 ConfirmedInventory
→ 表现控制器独立决定是否加速或减速
```

因此它们没有直接控制线，但具有生产者—消费者关系。

### 6.5 动画、音效和特效

回滚与逻辑追帧只重算逻辑，不能重复执行表现副作用：

- 回滚中间帧不逐帧渲染；
- Animator 混合权重不进入同步世界；
- 音效、粒子、震屏、伤害数字按事件 ID 去重；
- 重要且不可逆的事件，如正式得分和比赛结束，优先等待确认；
- 本地操作可预测播放轻量反馈，预测失败后平滑纠正，不重复播放确认版本。

## 七、确认库存耗尽时，远端是否会停住

确认帧暂时停止，并不意味着远端立即停住。

例如：

```text
ConfirmedFrame = 96
RemoteDisplayFrame = 93.5
```

表现层仍可继续播放已经确认的 94、95、96。短期乱序或丢包可能在库存耗尽前补齐，用户看不出问题。

库存耗尽后：

```text
RemoteDisplayFrame = ConfirmedFrame
```

严格确认模式只能停在最后确认状态。可选优化包括：

- 动态确认缓冲；
- 库存偏多时轻微加速；
- 库存偏少时轻微减速；
- 极短时间有限外推。

有限外推只是 View World 的临时预测，不属于 Confirmed World，仍有纠正风险。

## 八、TCP、UDP 与实时帧同步

### 8.1 TCP 的准确特点

同一条 TCP 连接保证可靠、有序的字节流交付：

```text
发送：Frame97 → Frame98 → Frame99
应用不会读取成：Frame99 → Frame97 → Frame98
```

但 TCP 不保存消息边界，可能发生拆包、粘包：

```text
一次Send ≠ 一次Receive
```

因此仍需固定长度或长度头进行消息分帧。

TCP 的主要实时性问题之一是队头阻塞：承载 Frame97 的数据丢失时，网络层即使已收到后续数据，也通常要等 97 重传成功后，才能按序交付给应用。

TCP 模式下常见的“逻辑帧落后”并不一定是乱序，而是：

```text
本地逻辑已运行到100
远端Actual只交付到96
```

### 8.2 UDP 的准确特点

UDP：

- 无连接语义；
- 不保证送达；
- 不保证顺序；
- 可能重复；
- 保留数据报边界；
- 后续包不会因前一包丢失而被传输层强制扣住。

UDP并不保证一定比TCP快。它的核心优势是：应用可以根据业务决定可靠性、顺序性、重传和过期策略。

### 8.3 裸 UDP 的问题

如果每帧输入只发送一次：

```text
97 丢失
98、99、100 到达
```

则：

```text
ConfirmedFrame 永久停在 96
```

因为确认世界不能越过 97 的输入空洞。

所以实时战斗不能简单采用“每帧只发一次、丢了就算”的裸 UDP。

## 九、UDP 输入可靠化与优化重点

### 9.1 最近多帧输入冗余

帧输入通常很小，可以让每个包携带最近若干帧：

```text
Packet105
├─ Input105
├─ Input104
├─ Input103
├─ Input102
└─ Input101
```

如果 Packet101 丢失，后续 Packet102、Packet103 仍会再次携带 Input101。单个包丢失一般只使该输入晚一个发包周期到达，而不是形成永久空洞。

与请求重传相比：

```text
请求重传：发现丢失 → 发请求 → 对方补发 → 收到
输入冗余：下一个正常包自动再次携带旧输入
```

### 9.2 序号、ACK 与 ACK 位图

典型 UDP 包头可包含：

```text
SessionID
PlayerID
PacketSequence
Ack
AckBits
LatestInputFrame
Inputs[]
```

`AckBits` 可以描述最近若干包的接收情况，帮助发送方发现缺失并选择性补发仍有价值的数据。

### 9.3 按帧幂等写入

由于冗余和重传，同一帧 Actual 可能多次到达：

```text
第一次收到相同 frameID → 写入
再次收到相同值          → 忽略
再次收到不同值          → 协议错误、作弊或数据损坏
```

网络包应先被解析，再把其中多个输入按 `frameID` 写入 InputLedger，而不是依赖 FIFO 到达顺序。

### 9.4 批量到包后的处理

网络恢复后可能一轮收到大量输入。正确流程：

```text
1. 排空本轮接收队列
2. 批量把所有 Actual 写入 InputLedger
3. 计算新的连续 ConfirmedThroughFrame
4. 找出本批次最早预测失配帧
5. 最多触发一次统一回滚
6. 在CPU预算内逐帧推进确认世界
```

输入可以批量入账，确认范围可以一次扩大，但确认世界必须顺序执行每一帧：

```text
Step(97) → Step(98) → Step(99) → Step(100)
```

不能只把 `ConfirmedFrame` 数字从 96 改成 100。

### 9.5 回滚前先合并全部新 Actual

假设同一轮收到 98、99，98 首先发现失配：

```text
错误做法：收到98回滚一次，收到99再回滚一次

正确做法：
先写入98和99
→ 找到最早失配帧98
→ 恢复97快照
→ 一次重演98到当前PredictedFrame
```

重演每帧重新查询 InputLedger：

```text
有Actual → 使用Actual
无Actual → 根据最新已知输入重新生成Predicted
```

后续预测不能机械复用旧值，因为更早的 Actual 变化可能改变预测基准。

## 十、KCP 是什么

KCP可以粗略理解为：

> 在 UDP 上实现的低延迟可靠传输协议。

典型能力包括：

- 包序号和 ACK；
- 超时与快速重传；
- 滑动窗口；
- RTT估算；
- 拥塞和发送控制；
- 分片与重组。

链路是：

```text
游戏应用 → KCP → UDP → IP
```

KCP与TCP相比更可配置，也可以使用更积极的重传策略，以更多带宽换取更低等待时间。但它无法消灭物理丢包；缺失数据仍需要补发。

### KCP与输入冗余不是同一概念

```text
KCP：通用可靠传输层
输入冗余：针对每帧小输入的业务级优化
```

两者可以组合，也可以按消息类型分通道：

| 消息类型 | 推荐思路 |
|---|---|
| 高频移动输入 | UDP＋最近输入冗余＋帧号去重 |
| 投篮、技能按键 | 输入冗余＋确认，必须最终到达 |
| 房间准备、加载完成 | KCP或其他可靠通道 |
| 比赛开始、比赛结束 | 可靠有序通道 |
| 过时后无价值的数据 | UDP，可直接丢弃旧包 |

所以“改用 UDP”不是简单替换 Socket，而是重新设计每类消息的可靠性语义。

## 十一、断网、重连与状态恢复

如果某个输入长期补不回：

```text
短期缺失
→ 预测 + 输入冗余 + ACK补发 + 表现缓冲

持续缺失
→ 远端表现停顿或有限外推 + 网络异常提示

超过阈值
→ 断线、重连、托管或比赛异常策略
```

不能把永久缺失的 Predicted 输入直接标记为 Actual，否则会破坏 Confirmed World 的定义。

### 11.1 当前转发服务器可以保存输入历史

服务器不一定运行篮球模拟，但可以缓存最近若干秒双方输入。重连客户端报告最后完整帧，服务器补发后续输入，客户端从快照重演。

### 11.2 从在线客户端获取确认快照

可以由仍在线客户端提供：

```text
ConfirmedSnapshot@N
+ N之后的Actual输入
+ SnapshotHash
```

重连端安装完整确认快照，再重演后续输入。必须设计快照提供者、帧号协商、Hash验证和不可信数据处理，不能只接收一个裸位置。

### 11.3 权威服务器快照

如果服务器运行篮球模拟并提供权威状态，就已经不是当前“服务器只转发输入”的纯结构，而是增加了服务器权威能力。

## 十二、性能成本

双世界的额外成本主要在纯确定性逻辑：

```text
总模拟Step数
≈ Predicted推进
 + Confirmed推进
 + 预测失配重演
 + 必要的逻辑追帧
```

稳定情况下，确定性模拟部分可能接近单世界的两倍，但渲染、Animator、粒子、摄像机和UI不需要运行两份，因此整款游戏的总成本通常不会简单翻倍。

内存主要包括：

- 两份当前世界状态；
- InputLedger；
- 两条轨道所需快照；
- 确认表现历史；
- 事件账本。

优化方法：

- 同步状态使用紧凑值类型；
- 只保存会影响未来逻辑的字段；
- 使用固定容量环形缓冲；
- 限制最大预测跨度和回滚窗口；
- 两条轨道不必保存同样深的历史；
- 回滚和追帧期间禁止重复表现副作用；
- 只在指定帧计算完整 Hash。

## 十三、最终心智模型

```text
                         ┌─────────────────────────────┐
本地Actual ─────────────→│                             │
远端Actual/Predicted ───→│ Predicted World             │
                         │ 低延迟运行到PredictedFrame   │
                         └──────────────┬──────────────┘
                                        │
                                        └→ 本地玩家表现

双方连续Actual ─────────→ Confirmed World
                         可靠运行到ConfirmedFrame
                                        │
                                        └→ 确认快照历史
                                                │
                                                └→ RemoteDisplayFrame
                                                    → 远端玩家表现

Confirmed + Predicted + 球权语义
                         └→ 篮球表现仲裁
```

最简洁的总结：

> Predicted World 用预测换取本地即时响应；Confirmed World 用等待换取远端可靠事实；View World 用确认库存、插值和有限调速隐藏短期网络抖动；UDP 网络层再用冗余、ACK、选择性补发和重连恢复，尽量在确认库存耗尽前补齐输入空洞。
