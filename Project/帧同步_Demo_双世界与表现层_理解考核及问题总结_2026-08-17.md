## 一、总体评价

当前水平可评为：**L2 稳定，开始进入 L3**。

- 已能正确推演大多数 Confirmed/Predicted 时间线，并理解预测错误会污染后续状态链。
- 已能解释固定延迟为什么不能保证远端安全，以及 Confirmed World 为什么能隔离预测回滚。
- 已能识别问题前提违反不变量；在 `ConfirmedFrame=110` 后又声称第 105 帧正常发生预测失配回滚时，能够直接指出场景不成立。这是 L3 的重要表现。

一句话判断：

## 二、帧同步 Demo 需要掌握到什么程度

### L1：能解释术语

能够准确解释：

- Actual、Predicted、Missing；
- ConfirmedFrame、PredictedFrame、RemoteDisplayFrame；
- Confirmed World、Predicted World、View World；
- Snapshot、Rollback、Replay、Interpolation、Extrapolation；
- 缓冲容量、播放延迟、确认库存。

只会背定义但不能推演具体帧号，还不足以调试 Demo。

### L2：能手工推演时间线

给定输入到达情况后，能够判断：

- ConfirmedFrame 能推进到哪里；
- 哪些帧使用 Actual，哪些帧使用 Predicted；
- 是否产生预测失配和纠正需求；
- 从哪个确认快照重建 Predicted World；
- 哪些旧快照必须丢弃；
- 远端表现是继续播放、减速、停顿还是有限外推。

这是理解和维护当前 Demo 的最低达标线。

### L3：能用不变量设计和诊断

能够主动使用以下不变量发现错误：

```text
ConfirmedFrame <= PredictedFrame
Confirmed World 每个已执行帧都具有双方 Actual
ConfirmedFrame 不能跨越输入空洞
Actual 是否齐全决定确认；Actual 是否命中预测决定是否纠正
正常推进与重演必须调用同一个确定性 Step
View World 不得写回 Confirmed/Predicted World
同一 canonical confirmed frame 的双方 Hash 必须一致
```

同时能够从日志判断：

- 位置修正来自预测回滚还是 View 外推收敛；
- 是输入账本错误、帧映射错误、确定性错误还是表现层错误；
- 最终 Hash 收敛为什么不能证明中间从未预测分叉。

这是独立负责帧同步 Demo 架构和疑难问题定位的达标线。

### L4：能实现并验证边界条件

能够完成并验证：

- 乱序、重复、延迟、丢失输入的 InputLedger；
- Confirmed/Predicted 双轨快照和重建；
- 不可变 Actual、最早失配帧和批量合并纠正；
- 远端确认表现、动态库存控制和有限外推；
- 持球、投篮、传球时的篮球表现源仲裁；
- 回滚事件去重、同帧 Hash、故障注入和双端自动化验收。

这是能够把原理稳定落成作品级 Demo 的水平。

## 五、目前最需要补强的五点

### 1. 把“确认”和“预测命中”彻底拆开

```text
双方 Actual 连续完整 → ConfirmedFrame 可以推进
Actual == Predicted   → 不需要纠正 Predicted World
Actual != Predicted   → 需要纠正 Predicted World
```

预测失败不阻止该帧成为确认帧；只要 Actual 已经完整，Confirmed World 就应使用 Actual 正确推进。

### 2. 把“输入空洞”和“纠正需求”彻底拆开

```text
前序 Missing          → 确认帧头不能越过
任意已到达 Actual 失配 → 已产生预测纠正需求
```

能否立即执行或是否合并纠正属于调度策略，不能说“有空洞就没有失配”。

### 3. 把“逻辑回滚”和“视觉收敛”彻底拆开

```text
Predicted World 错误 → 恢复确认快照 + Step重演
View 外推错误        → Transform平滑收敛或有限Snap
```

View 不运行篮球逻辑，也不能写回同步世界。

### 4. 诊断时必须记录数据来源

仅记录 `ViewFrame` 不够。建议最小字段：

```text
ViewFromFrame
ViewToFrame
ViewSource = Confirmed / Predicted / Extrapolated
ConfirmedFrame
PredictedFrame
RollbackErrorFrame
CorrectionReason = Rollback / Extrapolation / Catchup / Snap
```

只有“帧号 + 来源 + 触发原因”一起存在，才能解释同一次位置修正。

### 5. 从玩家位置扩展到篮球跨实体状态

篮球会同时依赖本地、远端和球权：

- 本地持球时可优先跟随 Predicted 本地玩家；
- 远端持球必须等 Confirmed 球权后再稳定附着；
- 本地投篮可即时预测离手；
- 预测失败时篮球只做有限表现收敛，不能污染 Confirmed World；
- 得分、比赛结束等不可逆事件通常需要确认后正式提交。

这一部分是从“能理解双世界”走向“能完成篮球帧同步 Demo”的关键缺口。

## 六、下一轮针对性考核题

### Q1：确认表现隔离

```text
ConfirmedFrame = 104
PredictedFrame = 110
RemoteView     = ConfirmedWorld[102 → 103]
第105帧 Actual 到达并推翻预测
```

Predicted World 重建 105～110 时，远端当前显示的 102→103 是否应该发生位置纠正？如果发生，说明哪层隔离失败？

### Q2：重复且冲突的 Actual

同一玩家第 120 帧 Actual 已记录为 A，之后又收到同帧但值为 B 的数据。InputLedger 应覆盖、忽略还是报告协议错误？为什么？

### Q3：同帧 Hash 故障定位

双方 `ConfirmedFrame=300`，输入账本逐帧完全一致，但 `ConfirmedHash[300]` 不同。这个问题更可能属于网络表现、预测策略还是确定性模拟？第一批应检查哪些字段？

### Q4：远端持球表现

Predicted World 判断远端第 200 帧拾到球，但 Confirmed World 只推进到 198。篮球能否立即挂到远端玩家手上？如果不能，如何避免篮球停顿得过于明显？

### Q5：本地预测投篮失败

本地 Predicted World 在 250 帧让篮球离手，但之后 Actual 证明投篮输入无效。哪些内容需要逻辑重建，哪些内容只能做视觉收敛，音效和粒子如何避免播放两次？

### Q6：确认库存控制

目标库存为 3 帧，当前库存从 5 降到 1。播放控制器应该何时加速、何时减速、何时外推、何时停顿？哪些阈值必须限制，避免速度来回振荡？

### Q7：日志归因

给定以下日志：

```text
ViewSource=Extrapolated
ViewFrom=410
ViewTo=411
ConfirmedFrame=409
CorrectionReason=Extrapolation
RollbackErrorFrame=-1
```

画面向后收敛时，为什么不能把它归因于逻辑回滚？

### Q8：最终收敛不等于中途一致

两个客户端最终在 ConfirmedFrame=500 的 Hash 相同，为什么仍不能证明 400～499 帧期间 Predicted World 从未分叉、远端画面从未纠正？还需要保存哪些轨迹证据？

## 七、建议的学习顺序

1. 用 10 组乱序/缺失/命中/失配帧号题，训练 `ConfirmedFrame` 与纠正需求的独立判断。
2. 用同一案例分别画出 Confirmed Track、Predicted Track、View Track，禁止混用“当前帧”一词。
3. 为每次纠正标记 `LogicReconcile` 或 `ViewConvergence`，训练层级归因。
4. 完成篮球四种来源切换：自由球、本地持球、远端持球、本地预测投篮。
5. 最后进入日志、Hash、事件去重和故障注入，达到可独立调试水平。

推荐下一轮先完成 Q1～Q3。通过标准不是只给结论，而是能写出：

```text
输入事实
→ 哪个帧头变化
→ 哪个世界推进或重建
→ View读取哪个来源
→ 是否需要逻辑回滚或视觉收敛
```

## 八、最终心智模型

```text
InputLedger 决定“我们知道了什么”
Confirmed World 表示“事实已经推演到哪里”
Predicted World 表示“为了低延迟暂时猜到哪里”
View World 决定“这一刻给玩家看什么”

确认推进、预测纠正、表现收敛是三条不同控制线。
```

当前最值得反复复述的一句话：

> Actual 是否连续完整决定确认世界；Actual 是否推翻预测决定预测世界；View 使用什么来源决定玩家看到停顿、回抽还是平滑收敛。
