## 问题 #1：预测+回滚系统在 200ms 高延迟下的 FIFO 顺序匹配失效

### 现象

当服务器设置为 200ms 延迟模式、两个客户端进行联机测试时：

1. 一方突然变向 → 触发回滚 → 方块抖动纠正位置 ✅（预期行为）
2. 但控制台持续输出 `预测=00000000, 实际=00000100` 的预测错误日志
3. 回滚持续触发直到约 33 帧后才稳定
4. 回滚结束后，**两边客户端的位置不一致**——一方已经走出去了，另一方被回滚拽回之前的位置（回滚把正确位置也撤销了）

```
控制台日志（节选）：
[PredictionSystem] ❌ 帧9预测错误: 预测=00000000, 实际=00000100
[Rollback] 回滚完成: safe=8 → 重放帧9
[PredictionSystem] ❌ 帧10预测错误: 预测=00000000, 实际=00000100
[Rollback] 回滚完成: safe=9 → 重放帧10
...
[Rollback] 回滚完成: safe=32 → 重放帧33
```

### 严重程度

🔴 **高** — 破坏了帧同步的最终一致性，属于功能不正确的级别。

---

### 根因分析

#### 根因 1：FIFO 顺序匹配假设在 >1 帧延迟下不成立

`PredictionSystem` v3（最终版）的核心假设是：**FIFO 队列中第 K 个到达的数据包，对应的是第 K 个被预测的帧。**

这个假设在 <= 1 帧延迟（≤33ms）时成立，但在 200ms 延迟（≈6~7 帧）下完全失效：

```
时间轴（实际运行过程）：
  帧 0:   无真实数据 → 预测（_lastRemoteInput=0x00000000）→ 队列: [0]
  帧 1:   无真实数据 → 预测（同上）→ 队列: [0, 1]
  帧 2:   无真实数据 → 预测 → 队列: [0, 1, 2]
  帧 3:   无真实数据 → 预测 → 队列: [0, 1, 2, 3]
  帧 4:   无真实数据 → 预测 → 队列: [0, 1, 2, 3, 4]
  帧 5:   无真实数据 → 预测 → 队列: [0, 1, 2, 3, 4, 5]
  ═══ 200ms 后，真实数据开始到达 ═══
  帧 6:   真实数据 0x0100 到达 → 弹帧 0 → 预测=0x00000000 → ❌ 回滚！
  （回滚到 safe= -1? 或 0？→ 初始位置丢失）
  帧 7:   真实数据 0x0100 到达 → 弹帧 1 → 预测=0x00000000 → ❌ 回滚！
  ...持续直到队列弹完（帧 0~6 总共 7 帧错误回滚）
```

**关键问题：** 队列里存储的帧号是**本地帧号**（0, 1, 2...），而远程玩家的输入是按**对端帧号**产生的。200ms 延迟下，远程玩家帧 0 的输入到达本地时，本地可能已经在执行帧 6 了。队列弹出了帧 0，但当前真实数据是帧 6 的——帧号完全错位。

#### 根因 2：DoRollback 只重跑单帧，不重跑后续帧

```csharp
// GameController.cs — DoRollback
void DoRollback(int errorFrame, uint correctRemoteRaw)
{
    int safeFrame = errorFrame - 1;
    _predictionSystem.RestoreSnapshot(safeFrame, ref _blockPosX, ref _blockPosZ);
    
    // 只重新执行了 errorFrame 这一帧
    // 但 errorFrame+1 到 currentFrame 的帧没有被重跑
    // 导致回滚的瞬间位置对了，但引擎继续跑后续帧时状态又乱了
}
```

回滚后只纠正了 errorFrame 一帧，但帧 10~33 仍然基于旧的错误预测执行。FrameEngine 的 while 追帧会继续从 safeFrame+1 跑到 currentFrame——但 DoRollback 里没有覆盖这个范围。

#### 根因 3：MarkRead 自动推进与回滚机制冲突（副因）

`FrameEngine.ExecuteOneFrame` 第 129 行每帧执行 `_frameBuffer.MarkRead(frameID - 4)`，这个 MarkRead 和服务器确认完全脱钩。虽然在快照系统（SnapshotBuffer）独立的情况下不直接影响快照，但 FrameBuffer 里的旧 Input 被提前标记为已消费，间接影响后续的帧查询。

### 建议修复方向

#### 方案 A：基于帧号偏移的回滚验证（推荐）

不做 FIFO 顺序匹配，改为携带帧号信息直接匹配：

```
客户端发送: SendInput(raw, localFrameID)  // 8 字节，已具备
服务器转发: Broadcast(raw, senderFrameID) // 8 字节，已具备
客户端接收: (raw, remoteFrameID)
      
验证逻辑:
  // remoteFrameID - estimatedDelay  ≈ 本地的预测帧号
  int predictedLocalFrame = remoteFrameID - ESTIMATED_DELAY_FRAMES;
  if (predictedLocalFrame >= 0 && 
      _predictionHistory.TryGetValue(predictedLocalFrame, out var predicted))
  {
      if (predicted._raw != raw) -> 回滚
  }
```

**优点：** 不依赖队列顺序，帧号直接匹配，精度高
**代价：** 需要估算 `ESTIMATED_DELAY_FRAMES`（可以用最近 N 个包的帧号差取平均）

#### 方案 B：拉长跳过帧数 + DoRollback 重跑全部后续帧（快速修复）

```csharp
// 1. SKIP_INITIAL_FRAMES 从 5 改为 60（≈2秒 200ms 延迟的缓冲）
const int SKIP_INITIAL_FRAMES = 60;

// 2. DoRollback 改为重跑 safeFrame+1 到 currentFrame 全部帧
void DoRollback(int safeFrame)
{
    RestoreSnapshot(safeFrame);
    for (int i = safeFrame + 1; i <= _frameEngine.CurrentFrame; i++)
    {
        // 用正确 Input + FrameBuffer 中的本地 Input 逐帧重跑
    }
}
```

**缺点：** 治标不治本，只是绕过了初始误报期，帧号错位问题仍存在

#### 方案 C：不用预测验证，改用权威服务器模式

不做预测验证回滚，改为服务器全权确认。客户端只管预测执行，不验证——服务器的确认到达后直接作为新的预测基准。

**缺点：** 回滚逻辑简化了，但"最终一致性"的保证从客户端的责任转移到了服务器，对 Demo 来说过度设计。

### 技术深度总结（作品集角度）

这个问题的本质暴露了**帧同步预测系统中一个经典的设计假设**：

| 假设 | 实际 | 后果 |
|------|------|------|
| 网络延迟 ≤ 1 帧间隔（33ms） | 实测 200ms ≈ 6~7 帧间隔 | FIFO 顺序匹配完全错位 |
| 本地帧号 == 远程帧号 | 双方帧号独立递增 | 无法直接做帧号减法对齐 |
| DoRollback 纠正一帧即可 | 后续帧仍然基于旧预测状态 | 回滚完状态又被覆盖 |

**解决方案的难点在于**：帧同步中客户端和服务器的帧号是独立序列，不能直接做减法。最简单的正确方案是方案 A——在 8 字节协议中已经携带了帧号，只是预测系统没有使用这个信息来做匹配，而是猜了一个 FIFO 顺序。

**这也说明了一个设计原则：当你的系统依赖"顺序"时，永远不要假设顺序能自然对齐——显式传递标识（帧号/seqnum）才是可靠的。**
