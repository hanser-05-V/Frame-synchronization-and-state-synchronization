## 问题 #1：预测+回滚系统在 200ms 高延迟下的 FIFO 顺序匹配失效

### 现象

当服务器设置为 200ms 延迟模式、两个客户端进行联机测试时：

1. 一方突然变向 → 触发回滚 → 方块抖动纠正位置 ✅（预期行为）
2. 但控制台持续输出 `预测=00000000, 实际=00000100` 的预测错误日志
3. 回滚持续触发直到约 33 帧后才稳定
4. 回滚结束后，**两边客户端的位置不一致**——一方已经走出去了，另一方被回滚拽回之前的位置（回滚把正确位置也撤销了）

```
控制台日志（节选）：
[PredictionSystem] ❌ 帧9预测错误: 预测=00000000, 实际=00000100
[Rollback] 回滚完成: safe=8 → 重放帧9
[PredictionSystem] ❌ 帧10预测错误: 预测=00000000, 实际=00000100
[Rollback] 回滚完成: safe=9 → 重放帧10
...
[Rollback] 回滚完成: safe=32 → 重放帧33
```

### 严重程度

🔴 **高** — 破坏了帧同步的最终一致性，属于功能不正确的级别。

---

### 根因分析

#### 根因 1：FIFO 顺序匹配假设在 >1 帧延迟下不成立

`PredictionSystem` v3（最终版）的核心假设是：**FIFO 队列中第 K 个到达的数据包，对应的是第 K 个被预测的帧。**

这个假设在 <= 1 帧延迟（≤33ms）时成立，但在 200ms 延迟（≈6~7 帧）下完全失效：

```
时间轴（实际运行过程）：
  帧 0:   无真实数据 → 预测（_lastRemoteInput=0x00000000）→ 队列: [0]
  帧 1:   无真实数据 → 预测（同上）→ 队列: [0, 1]
  帧 2:   无真实数据 → 预测 → 队列: [0, 1, 2]
  帧 3:   无真实数据 → 预测 → 队列: [0, 1, 2, 3]
  帧 4:   无真实数据 → 预测 → 队列: [0, 1, 2, 3, 4]
  帧 5:   无真实数据 → 预测 → 队列: [0, 1, 2, 3, 4, 5]
  ═══ 200ms 后，真实数据开始到达 ═══
  帧 6:   真实数据 0x0100 到达 → 弹帧 0 → 预测=0x00000000 → ❌ 回滚！
  （回滚到 safe= -1? 或 0？→ 初始位置丢失）
  帧 7:   真实数据 0x0100 到达 → 弹帧 1 → 预测=0x00000000 → ❌ 回滚！
  ...持续直到队列弹完（帧 0~6 总共 7 帧错误回滚）
```

**关键问题：** 队列里存储的帧号是**本地帧号**（0, 1, 2...），而远程玩家的输入是按**对端帧号**产生的。200ms 延迟下，远程玩家帧 0 的输入到达本地时，本地可能已经在执行帧 6 了。队列弹出了帧 0，但当前真实数据是帧 6 的——帧号完全错位。

#### 根因 2：DoRollback 只重跑单帧，不重跑后续帧

```csharp
// GameController.cs — DoRollback
void DoRollback(int errorFrame, uint correctRemoteRaw)
{
    int safeFrame = errorFrame - 1;
    _predictionSystem.RestoreSnapshot(safeFrame, ref _blockPosX, ref _blockPosZ);
    
    // 只重新执行了 errorFrame 这一帧
    // 但 errorFrame+1 到 currentFrame 的帧没有被重跑
    // 导致回滚的瞬间位置对了，但引擎继续跑后续帧时状态又乱了
}
```

回滚后只纠正了 errorFrame 一帧，但帧 10~33 仍然基于旧的错误预测执行。FrameEngine 的 while 追帧会继续从 safeFrame+1 跑到 currentFrame——但 DoRollback 里没有覆盖这个范围。

#### 根因 3：MarkRead 自动推进与回滚机制冲突（副因）

`FrameEngine.ExecuteOneFrame` 第 129 行每帧执行 `_frameBuffer.MarkRead(frameID - 4)`，这个 MarkRead 和服务器确认完全脱钩。虽然在快照系统（SnapshotBuffer）独立的情况下不直接影响快照，但 FrameBuffer 里的旧 Input 被提前标记为已消费，间接影响后续的帧查询。

### 建议修复方向

#### 方案 A：基于帧号偏移的回滚验证（推荐）

不做 FIFO 顺序匹配，改为携带帧号信息直接匹配：

```
客户端发送: SendInput(raw, localFrameID)  // 8 字节，已具备
服务器转发: Broadcast(raw, senderFrameID) // 8 字节，已具备
客户端接收: (raw, remoteFrameID)
      
验证逻辑:
  // remoteFrameID - estimatedDelay  ≈ 本地的预测帧号
  int predictedLocalFrame = remoteFrameID - ESTIMATED_DELAY_FRAMES;
  if (predictedLocalFrame >= 0 && 
      _predictionHistory.TryGetValue(predictedLocalFrame, out var predicted))
  {
      if (predicted._raw != raw) -> 回滚
  }
```

**优点：** 不依赖队列顺序，帧号直接匹配，精度高
**代价：** 需要估算 `ESTIMATED_DELAY_FRAMES`（可以用最近 N 个包的帧号差取平均）

#### 方案 B：拉长跳过帧数 + DoRollback 重跑全部后续帧（快速修复）

```csharp
// 1. SKIP_INITIAL_FRAMES 从 5 改为 60（≈2秒 200ms 延迟的缓冲）
const int SKIP_INITIAL_FRAMES = 60;

// 2. DoRollback 改为重跑 safeFrame+1 到 currentFrame 全部帧
void DoRollback(int safeFrame)
{
    RestoreSnapshot(safeFrame);
    for (int i = safeFrame + 1; i <= _frameEngine.CurrentFrame; i++)
    {
        // 用正确 Input + FrameBuffer 中的本地 Input 逐帧重跑
    }
}
```

**缺点：** 治标不治本，只是绕过了初始误报期，帧号错位问题仍存在

#### 方案 C：不用预测验证，改用权威服务器模式

不做预测验证回滚，改为服务器全权确认。客户端只管预测执行，不验证——服务器的确认到达后直接作为新的预测基准。

**缺点：** 回滚逻辑简化了，但"最终一致性"的保证从客户端的责任转移到了服务器，对 Demo 来说过度设计。

---

### 技术深度总结（作品集角度）

这个问题的本质暴露了**帧同步预测系统中一个经典的设计假设**：

| 假设 | 实际 | 后果 |
|------|------|------|
| 网络延迟 ≤ 1 帧间隔（33ms） | 实测 200ms ≈ 6~7 帧间隔 | FIFO 顺序匹配完全错位 |
| 本地帧号 == 远程帧号 | 双方帧号独立递增 | 无法直接做帧号减法对齐 |
| DoRollback 纠正一帧即可 | 后续帧仍然基于旧预测状态 | 回滚完状态又被覆盖 |

**解决方案的难点在于**：帧同步中客户端和服务器的帧号是独立序列，不能直接做减法。最简单的正确方案是方案 A——在 8 字节协议中已经携带了帧号，只是预测系统没有使用这个信息来做匹配，而是猜了一个 FIFO 顺序。

**这也说明了一个设计原则：当你的系统依赖"顺序"时，永远不要假设顺序能自然对齐——显式传递标识（帧号/seqnum）才是可靠的。**

## 问题 #2：预测验证"张冠李戴" — 到达即用消费下，误报回滚抹掉对手真实位移（v10）

### 现象

双客户端联机（TCP ≈200ms 延迟），P2 持续按键移动后松手停止：

1. P1 控制台报"预测错误"并触发回滚"纠正" ✅（看似预期行为）
2. P1 画面上 P2 的方块**突然回跳一下**（顿一下），然后停止
3. **双端最终停止位置不一致**——P1 端的 P2 比 P2 自己客户端**少走约 1 个单位**（≈6~7 帧位移）
4. 最反直觉的一点：**回滚触发前的那一瞬间位置本来是对的**，是"纠正"动作把对的位置改错了

```
控制台日志（P1）：
[PredictionSystem] ❌ 帧2791预测错误: 预测=00000700, 实际=00000000, 清除6条
[Rollback] 帧2791预测错误，开始回滚纠正
[Rollback] 回滚完成: safe=2790 → 重放帧2791..2798 (纠正远程Input: 00000000)
```

### 严重程度

🔴 **高** — 对手每次"移动→停止"（按键 ≥0.25 秒必然发生）**100% 误触发回滚**，且每次回滚都抹掉一段真实位移，最终一致性被系统性破坏。

---

### 根因分析

#### 根因 1（主犯）：验证逻辑"张冠李戴" — 账本上记的 ≠ 实际用的

`PredictionSystem.cs:53` 每帧先存 `_predictionHistory[frameID] = _lastRemoteInput`（**进帧前的旧值**），而本帧真正执行用的是刚出队的真实包（`:105`）。验证时（`:63-68`）拿 `history[F-6]` 对比"当前刚到的包"：

```
P1本地帧:    2790   2791   2792 ... 2796   2797
出队真实包:  0x700  0x700  0x700 ... 0x700  0x0000 ← P2松手的包到了
实际使用:    真实   真实   真实  ... 真实   真实   ← 全程没预测过！
history[F]:  0x700  0x700  0x700 ... 0x700  0x700  ← 记的全是"上一帧的真实值"

验证@2797:  history[2791]=0x700 vs 当前包0x0000 → "❌帧2791预测错误"（误报）
```

它实际比较的是 **"对手约13帧前的真值" vs "对手约6帧前的真值"**——两个都是真实输入、帧还不同。这不是预测校验器，是**输入变化探测器**：对手任意一次"动→停"必报警。更讽刺的是 `:68` 的 `predicted._raw != 0` 守卫把"停→动"半边压掉了，而"预测对手静止、对手实际动了"恰恰是**真正需要回滚**的场景——所以现状是：**该响的时候永远不响，不该响的时候必响。**

#### 根因 2（偏差直接元凶）：回滚用"一个平值"重写 6~8 帧真实历史

`GameController.cs:397-404` 重放时 `i >= errorFrame` 的所有帧远程输入统一改为 `correctRemoteRaw(=0x0000)`。但帧 2791..2796 当时执行用的是**真实移动包**——P2 自己的客户端走满了这些步。回滚 = 恢复 2790 快照撤销一切 + 用 0 重写 → 这 6~7 帧真实位移**蒸发**（≈6.5帧 × 5×0.033 ≈ 1.07 单位）。即"顿一下（瞬间回跳）+ 最终位置偏差"。

#### 根因 3：回滚重放中二次消费网络队列（偷走未来输入）

`GameController.cs:399-402` 重放循环内每帧再调 `TryGetRemoteInput`，最多偷走 8 个尚未轮到的远程输入。本次日志里偷到的恰好都是 0x0000 没放大危害；若对手正在移动中触发回滚，每次回滚都会额外丢步。

#### 根因 4：重放窗口越界一帧 — 重放了尚未执行的帧，本地玩家位移双算

`FrameEngine.cs:110` `_currentFrame++` 在回调**之前**执行 → `OnFrameUpdate(2797)` 时 `CurrentFrame` 已是 2798。`DoRollback`（`GameController.cs:376,384`）重放到 2798——该帧还没执行，FrameBuffer 取不到本地输入 → **现场读键盘**（`:393`，不确定性来源），随后引擎又正常执行一遍 2798 → 本地玩家该帧位移**双算**。

#### 结构性结论

协议明明已传 `remoteFrameID`（`NetworkClient.cs:69-77` 8字节协议），但消费端用的是**丢弃帧号的单参** `TryGetRemoteInput`（`GameController.cs:159`）——远程输入"**到达即用**"，无帧对齐。没有"本地帧 F 本该用对手哪一帧输入"的确定映射，**预测、验证、回滚三件事全都没有定义**。

---

### 理解检验与纠偏（帅老大自述理解 → 架构导师逐条评判）

**✅ 抓准的核心**：①「这里其实根本没有进行预测」——完全正确，本次全程用真实包，"预测错误"是账本错位的误报，这是整个 Bug 的题眼；②方案A 后半段（回滚时该帧已有真值→用真值重放→后续帧接着预测）正确。

| # | ❌ 原表述 | 错在哪 | 正确是什么 | 为什么 |
|---|----------|--------|-----------|--------|
| 1 | 「远端采用7帧前的实际输入执行 → 导致位置偏移」 | 把"延迟"当成偏差来源 | 延迟消费只造成**时间平移**，不造成终点偏差；偏差来自回滚抹史。回滚前位置本来是对的，被"纠"错了 | TCP 不丢不乱序，每个移动包恰好消费一次 → **总位移守恒**；破坏守恒的只有预测补帧（双算）或回滚改史（蒸发） |
| 2 | 「触发回滚时会发生追帧」 | 回滚重放 ≠ 追帧 | 追帧 = 引擎因时间落后连跑**新帧**（`FrameEngine.cs:93-104`，有 ⚡日志）；回滚重放 = `DoRollback` 内对**已执行旧帧**手动重算 | 对象不同（新帧 vs 旧帧）、入口不同（Update 循环 vs 回调内同步调用）；日志中无"⚡追帧" |
| 3 | 「7帧前输入再执行一遍，本地多执行两次移动」 | 方向反了、对象错了 | 远端角色是**少执行**（6~7帧被抹掉一次都没留下）；真正"多执行一遍"的是根因4——**本地玩家、仅1帧** | 回滚 = 撤销+重写，最终状态只取决于重写用的输入；重写用 0 位移就是 0。"双算"属于另一场景（队列空时预测补帧+迟到包再消费的静默漂移） |
| 4 | 「方案A = 提前进行预测，两端输入对比」 | "提前"不是本质；"两端对比"有歧义 | 本质是**贴帧号建确定映射** `dict[F-offset]`：命中用真实、缺失才预测（打标记）；对比是**同帧、同玩家（远端）**的 `used[F]` vs `actual[F]` | 预测时机没变，变的是"这帧本该是什么"从此有定义；用了真实值的帧不可能错、永不需验证 |
| 5 | 「方案B 相当于不处理」 | 说过头了 | B 修真缺陷（根因3/4：偷队列、越界双算、LateUpdate时序）——**有效、但不对症** | 根因1（误报）与根因2（平值抹史）一个没碰，本症状原样复现 |

### 建议修复方向

#### 方案 A：帧对齐预测回滚（推荐，提前阶段4的一小块）

```
1. NetworkClient: FIFO → Dictionary<int,uint>（按 remoteFrameID 索引），
   提供 TryGetRemoteInputAt(remoteFrame) + 水位清理
2. ReadInputs: 首包锚定 offset = localFrame - remoteFrameID；
   本地帧F 的远程输入 = dict[F-offset]，命中=真实、缺失=预测（重复上一真值）
3. PredictionSystem: history 存"实际使用值 + 是否预测标记"；
   验证 = 同帧比对 used[F] vs actual[F]，只有真预测错才回滚
4. DoRollback: 重放终点=最后已执行帧(CurrentFrame-1)；逐帧远程输入从 dict 取真值、
   缺失用纠正后预测；本地输入只从 FrameBuffer 取（禁止现场读键盘）；
   禁止消费网络队列；纠正值回写 FrameBuffer；回滚挪到 LateUpdate
```

**优点：** 预测/验证/回滚三件事第一次有了定义；双端 (帧→输入) 映射一致，为阶段4 MD5 脱同步检测打底；与"FIFO→帧ID字典"的既定方向一致，非丢弃式工作。

#### 方案 B：原路线最小三项（LateUpdate + 移除重放中取队列 + IsValid）

**缺点：** 只治根因3/4。验证无定义（根因1）与平值抹史（根因2）仍在——对手一停就误回滚、终点偏差**原样复现**。有效但不对症。

### 技术深度总结（作品集角度）

| 隐含假设 | 实际 | 后果 |
|------|------|------|
| history 里记的 = 该帧实际用的 | 存的是进帧前旧值 | 验证器退化成"输入变化探测器" |
| 队头包 ↔ 当前帧天然对应（到达即用） | 包对应发送方约6帧前的输入 | "预测错误"根本无定义 |
| 回滚用一个纠正值重写整段即可 | 被重写的每帧各有自己的真值 | 对手真实位移被抹掉 → 永久偏差 |
| 重放到 CurrentFrame 即"当前帧" | 回调时 CurrentFrame 已 +1 | 重放未执行帧 → 本地位移双算 |

**三条设计原则：**

1. **位移守恒视角**：TCP 全量有序下，延迟只平移轨迹、不改终点；破坏守恒的只有"补帧双算"和"改史蒸发"。任何纠正机制必须以**每帧真值**为单位操作，绝不能用平值批量重写。
2. **与问题 #1 同根**：#1 错在 FIFO 顺序隐式对齐，#2（v10）换成"时间偏移回查"仍是隐式对齐——**只要不显式贴帧号，换多少种猜法都会失效**。协议里的 `remoteFrameID` 从 v3 起就传了，一直没被消费端用上。
3. **验证器必须比较同一对象**：`used[F]` vs `actual[F]`——帧号相同、玩家相同，才叫"预测验证"；否则比出来的只是"输入变没变"。
